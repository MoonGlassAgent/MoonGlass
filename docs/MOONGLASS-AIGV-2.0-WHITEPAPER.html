摘要

AIGV 2.0 的目标不是"让 AI 辅助 DV 工程师写更多 testcase"，而是建立一套机器可自主执行的验证空间探索、判定与收敛体系。系统以 Verification Space Builder 为核心，将 Spec 与 RTL 转化为结构化、可查询、可更新的五维验证空间；通过 Explorer/Planner 自主决定"测什么"；通过 Multi-Oracle 独立判定"对不对"；通过 Novelty Saturation 与 Risk-weighted Mutation 决定"够不够"；最终由 Closure Engine 输出机器 Sign-off 建议。

本白皮书给出 AIGV 2.0 的核心数据模型（Scenario Schema）、四层架构、模块设计、状态转换规则、层间接口契约和 v0.1 PoC 验收标准。所有设计均以"第一版可在一个 Sprint 内跑通闭环"为约束。

关键词：AIGV；自主验证；Verification Space；Scenario Schema；Explorer；Closure Engine；Risk-weighted Mutation；Novelty Saturation；ASIC IP

1. 核心定义

AIGV 2.0 的 Sign-off 依据不是"AI 认为设计没问题"，而是以下工程条件的联合满足：

  1. 验证空间已被系统探索：机器显式构造了 Feature × Boundary × Interaction × Temporal × State 五维验证空间，所有关键区域均获得覆盖证据或不可达证明。
  2. 所有关键 Scenario 获得独立 Oracle 证据：每个关键 Intent 至少由两个独立来源的 Oracle（Reference Model、Invariant、Protocol Checker、Metamorphic Relation、End-to-End Semantic Checker 等）共同判定为 PASS。
  3. 主动攻击无法产生有意义的新空间：Explorer Agent 在预算内连续 N 轮未能发现新的高风险 Scenario（Novelty Saturation），证明验证边际信息收益趋近于零。
  4. 验证体系具有足够的缺陷敏感性：Risk-weighted Mutation Score 达到项目定义阈值，且所有未被检测到的 mutant 均经过审查确认为等价变异或低影响区域。
  5. 无未解释的 Oracle 冲突、Protocol 违规、Invariant 破坏或 Regression 失败。
  6. 所有证据可追溯、可复现、可审计：从 Requirement 到 Verification Intent 到 Scenario 到 Test 到 Evidence 保持完整追踪链。
机器 Sign-off 条件：当且仅当以上六项条件同时满足时，Closure Engine 可输出机器 Sign-off 建议，供工程师最终审批。工程师的审批不是"再检查一遍 AI 的结论"，而是"确认 Sign-off 条件已按定义满足，且剩余风险有明确记录"。

2. 设计哲学

2.1 替代而非辅助

AIGV 1.0 解决的是"AI 参与验证时如何保证不胡说"。AIGV 2.0 解决的是"AI 如何自己完成验证，并知道何时可以 Sign-off"。两者的关系是框架层 + 引擎层：Governance 保证机器不胡来；Intelligence 代替 DV 决定测什么；Execution 代替 DV 执行测试；Judgment 代替 DV 判定对错和决定何时结束。

2.2 程序产生事实，AI 做语义剪枝

Feature 提取、结构分析、Interaction 发现、Boundary 枚举由确定性程序完成；AI 只负责"哪些组合在架构语义上值得形成 Scenario"。这避免了 LLM 幻觉污染验证空间的基础事实层。

2.3 Negative Space 是 first-class citizen

验证空间不仅记录"测了什么"，还系统记录"为什么不测某些空间"。未验证 ≠ 漏验证。每个 EXCLUDED、UNREACHABLE、SPEC_UNDEFINED 都必须携带明确原因和证据。

2.4 五维坐标是描述体系，不是计算空间

Feature × Boundary × Interaction × Temporal × State 是 Scenario 的坐标系，不要求暴力计算 Cartesian Product。Scenario 必须同时满足结构上可交互、协议上合法、状态上可达、语义上有意义，才能进入候选池。

2.5 不依赖 Bug History

AIGV 2.0 主路径的输入只有：SPEC、RTL、Protocol、Architecture Constraints、Verification State、Simulation Results、Coverage。Bug history 可作为可选增强（fine-tuning / RAG），但不能进入核心方法学，以保证新 IP 从第一天就能冷启动。

4. Verification Space Model

4.1 五维坐标体系

维度语义离散化规则
FeatureSpec 功能点或 RTL 结构特征按 Spec 章节 + 结构类型（CONTROL_EVENT / DATA_PATH / CONFIG / STATUS / ERROR）分类
Boundary数学边界或协议边界0, 1, MAX-1, MAX, overflow/wrap 等
InteractionFeature 之间的结构关系DIRECT（共享 state/register）、INDIRECT（COI overlap）、PRIORITY（同一 priority chain）、DEPENDENCY（enable/condition 控制）
Temporal事件之间的时序关系BEFORE, SAME_CYCLE, AFTER, WITHIN_N_CYCLES
State系统生命周期状态主要 FSM states，按可达性分层

4.2 空间不是 Cartesian Product

VerificationSpace = { s | Valid(s) ∧ Relevant(s) }

Scenario 必须同时满足：

  • 结构上可交互：Feature 之间在 RTL 中有物理交互路径（Interaction Builder 规则判定）
  • 协议上合法：输入序列符合 AXI/APB 等协议约束（Protocol Legalizer 过滤）
  • 状态上可达：起始状态在当前模型下可达（Formal cover 或仿真预热确认）
  • 语义上有意义：组合在架构层面有验证价值（AI 语义剪枝）

4.3 Negative Space

Negative Space 记录"明确不验证"的区域，与 Positive Space 同等重要：

分类含义关闭证据
ARCHITECTURALLY_INVALID架构上不可能发生Spec 章节引用 / 协议约束说明
UNREACHABLE_BY_CONSTRAINT当前约束下不可达Formal 不可达证明 / 约束文档
PROTOCOL_ILLEGAL违反协议合法性Protocol checker 规则引用
OVER_BUDGET超出验证预算且风险极低Risk 评分 + 预算审批记录

6. 核心模块设计（v0.1）

6.1 Feature Extractor

项规格
输入Spec（自然语言/结构化）、RTL、寄存器定义、接口定义
输出有限 Feature 集合，每个 Feature 携带 Semantic Type Tag
实现LLM 从 Spec 提取初稿 + 工程师一次性确认
约束Feature taxonomy 是低频变化数据，v0.1 不要求全自动化
Feature Semantic Type Tag 必须包含：type（CONTROL_EVENT / DATA_PATH / CONFIG / STATUS / ERROR）、triggers、affects、boundaries、temporal_scope。Type 决定 Dimension Expander 的适用规则。

6.2 Structural Analyzer

项规格
输入RTL（SystemVerilog）
输出FSM、signal dependency、register writer、condition tree、counter、FIFO、resource、clock/reset domain、request/response path
工具Slang AST（优先）或 Verilator fallback
约束必须尽量 deterministic，输出结构化 JSON

6.3 Interaction Builder

核心原则：规则驱动，AI 只做语义剪枝。

规则 ID条件Interaction 类型优先级
RULE-I01两个 Feature 修改同一个 state/registerDIRECT_INTERACTIONP0
RULE-I04多个 Feature 出现在同一个 priority chainPRIORITY_INTERACTIONP1
RULE-I02两个 Feature 的 COI overlapINDIRECT_INTERACTIONP2
RULE-I03Feature A 改变 Feature B 的 enable/conditionDEPENDENCY_INTERACTIONP3（v0.1 可暂不处理）
RULE-I05request 与 response 跨周期关联TEMPORAL_INTERACTION自动附加
剪枝规则：每个 Feature 最多保留 5 个 Interaction（按 risk_score 排序）；丢弃的进入 PRUNED 状态并记录原因。

6.4 Dimension Expander

对每组 Interaction，自动展开 Boundary、Temporal、State 维度，生成为 candidate Scenario Pool。

Interaction: abort × bvalid ↓ Boundary: outstanding = {0, 1, MAX-1, MAX} Temporal: {BEFORE, SAME, AFTER} State: {FETCH, ISSUE, WAIT_RESP} ↓ Candidate Pool: 理论 4×3×3 = 36 ↓ Validity Engine 过滤 ↓ Valid Candidates: 通常 5-12 个

6.5 Validity Engine（v0.1 硬规则）

规则判定理由
(abort, outstanding=0)INVALIDabort 时 outstanding 必须 >0 才有意义
(reset, ANY)VALID_BUT_DOMINATESreset 覆盖其他所有状态，需特殊处理
(timeout, outstanding=0)INVALID无 outstanding 事务时不会 timeout
(bvalid, state=IDLE)INVALIDIDLE 状态下不会有 response 到达
(outstanding=MAX, backpressure=sustained)VALID_HIGH_RISK合法但极端，标记为高风险

6.6 Space Database

v0.1 使用 SQLite + JSON fields，不引入图数据库。

-- 核心表 CREATE TABLE scenarios ( scenario_id TEXT PRIMARY KEY, feature_set JSON NOT NULL, boundary JSON, interaction_type TEXT, interaction_object TEXT, temporal JSON, state TEXT, risk_score REAL, risk_markers JSON, status TEXT CHECK(status IN ( 'DISCOVERED','PLANNED','EXECUTED','VERIFIED', 'FAILED','NOT_REACHED','EXCLUDED','UNREACHABLE', 'SPEC_UNDEFINED','CONFLICT' )), exclusion_reason TEXT, exclusion_class TEXT, novelty_score REAL, novelty_details JSON, expected_cost REAL, rtl_hash TEXT, version INTEGER DEFAULT 1, created_at TIMESTAMP, updated_at TIMESTAMP ); CREATE TABLE executions ( execution_id TEXT PRIMARY KEY, scenario_id TEXT REFERENCES scenarios(scenario_id), test_id TEXT, reach_status TEXT, simulation_time REAL, wall_clock_time REAL, raw_results_path TEXT, log_path TEXT, waveform_path TEXT, coverage_delta JSON, executed_at TIMESTAMP ); CREATE TABLE oracle_results ( result_id TEXT PRIMARY KEY, execution_id TEXT REFERENCES executions(execution_id), oracle_type TEXT, oracle_source TEXT, independence_level INTEGER, verdict TEXT, evidence_path TEXT, confidence REAL );

7. 状态机与转换规则

DISCOVERED ├──→ PLANNED (Planner 选中) ├──→ EXCLUDED (Validity Engine 判定非法) └──→ SPEC_UNDEFINED (需要规格澄清) PLANNED ├──→ EXECUTED (Cocotb 运行完成) └──→ EXCLUDED (执行前发现新的排除理由) EXECUTED ├──→ VERIFIED (所有 Oracle PASS + 证据完整) ├──→ FAILED (至少一个 Oracle FAIL) ├──→ NOT_REACHED (仿真未触发场景) └──→ CONFLICT (Oracle 结论矛盾) VERIFIED ├──→ DISCOVERED (RTL 变更，且 scenario 在 affected 集中) └──→ STALE (RTL 变更，但不在 affected 集中，快速验证即可) FAILED ├──→ PLANNED (修复后重跑) └──→ EXCLUDED (确认为工具/环境错误，非设计问题) NOT_REACHED ├──→ PLANNED (调整激励后重跑) ├──→ UNREACHABLE (Formal 证明不可达) └──→ EXCLUDED (确认为架构上不可触发) CONFLICT ├──→ PLANNED (人工仲裁后重跑) └──→ EXCLUDED (确认为 Oracle 错误) EXCLUDED / UNREACHABLE / SPEC_UNDEFINED └──→ DISCOVERED (RTL/规格变更后重新评估)
关键规则：VERIFIED → DISCOVERED 的触发条件必须精确计算（基于 COI 影响分析），不能 RTL 有任何变动就全部重开。COI 深度限制在 3 层以内，超出视为未受影响。

8. Explorer & Planner

8.1 Explorer v0.1：Ranking Engine（非 RL）

v0.1 不使用强化学习。Explorer 是一个纯排序引擎，每轮从候选池中选择 Top-K Scenario。

Priority = (Risk × Novelty × CoverageGap × ReachabilityConfidence) / ExpectedCost
因子计算方式范围
Riskrisk_score from Structural Analyzer0-1
Noveltynovelty_score from Space DB，归一化0-1
CoverageGap1 - (verified_scenarios / total_scenarios_for_this_feature)0-1
ReachabilityConfidenceValidity Engine 的可达概率估计0-1
ExpectedCost基于历史同类型 scenario 的平均仿真时间>0，单位 CPU-seconds

8.2 Novelty 评分（v0.1）

Novelty = α·NewDimension + β·CombinationNovelty + γ·StateDistance + δ·PathNovelty

v0.1 简化实现：

  • 新 Feature 组合发现：+10
  • 新 Temporal 关系发现：+5
  • 新 Boundary 组合发现：+3
  • 已覆盖但新路径到达：+1
  • 重复已有 Scenario：-5

8.3 Planner 批次选择

def select_next_batch(budget_cpu_seconds, max_scenarios=20): candidates = db.query(""" SELECT * FROM scenarios WHERE status IN ('DISCOVERED', 'NOT_REACHED') ORDER BY priority DESC """) selected = [] remaining_budget = budget_cpu_seconds for scn in candidates: if scn.expected_cost <= remaining_budget and len(selected) < max_scenarios: selected.append(scn) remaining_budget -= scn.expected_cost else: break return selected

9. Multi-Oracle 体系

9.1 Oracle 类型与独立性

Oracle来源独立性判定什么
Reference ModelSpec → 独立 Python AgentLevel 1Architectural output 是否匹配
InvariantArchitecture rulesLevel 2全局状态一致性
ProtocolAXI VIP / 第三方 checkerLevel 3协议合规性
End-to-EndSpec → 独立 LLM AgentLevel 1IO 语义正确性
MetamorphicTransform logicLevel 2变换前后 functional 等价性

9.2 独立性要求

关键规则：关键 Scenario 必须至少有两个 Independence Level ≥ 2 的 Oracle 同时 PASS，才允许进入 VERIFIED 状态。如果所有 Oracle 都是 Level 1 且同源（如同一个 Spec 理解），不允许自动 sign-off，必须人工审查。

9.3 矛盾仲裁

场景判定
Reference PASS，Invariant FAIL以 Invariant 为准（Invariant 是架构级硬约束）
Protocol PASS，End-to-End FAIL以 End-to-End 为准（用户关心数据正确，非协议合规）
Metamorphic PASS，Reference FAIL以 Reference 为准（Metamorphic 只验证关系）
两个独立 Oracle 结论相反标记 CONFLICT，进入人工审查队列

10. Closure Engine

10.1 停止条件

当且仅当以下全部满足，Closure Engine 输出机器 Sign-off 建议
条件阈值说明
Requirement Coverage100%所有 P0/P1 REQ 映射到 VERIFIED Intent
Critical Scenario Coverage≥ target项目定义，通常 95%+
Risk-weighted Mutation Score≥ target项目定义，通常 90%+
Critical Unknown0无未解释的高风险 UNKNOWN Scenario
Oracle Violation0无未修复的 FAIL/CONFLICT
RegressionPASS全部回归无失败
Novelty Saturation连续 N 轮 < ε验证边际信息收益趋近于零

10.2 Novelty Saturation

Δ Novelty / Δ SimulationBudget → 0

具体指标：

  • 每轮 1000 个 scenario 执行后，统计新发现的高风险 scenario 数量
  • 连续 N 轮（新 IP 建议 N=3-5，成熟 IP 建议 N=5-10）新发现数量 < ε（建议 ε=1-2）
  • 同时 Mutation Score 已达到阈值

10.3 Risk-weighted Mutation Score

M_risk = Σ Detect(m_i) × Weight(m_i) / Σ Weight(m_i)

Weight 来自 Risk Analysis 输出：

Mutation 类型Weight来源 Risk
控制状态机优先级 mutation10R02 PRIORITY_DEPENDENCY
Transaction accounting mutation10R04 OUTSTANDING_DEPENDENCY
边界条件 mutation8R05 COUNTER_BOUNDARY
错误处理 mutation8R07/R11 ERROR_TIMEOUT
数据通路 mutation5低结构风险区域
状态/debug mutation2非 architectural 区域

12. v0.1 PoC 计划

12.1 目标 IP 范围

目标：AXI DMA Controller（简化版）
支持 Feature：abort, timeout, outstanding, response, reset
支持 Boundary：outstanding = {0, 1, MAX-1, MAX}
支持 Temporal：{BEFORE, SAME, AFTER}
支持 State：{IDLE, ACTIVE, WAIT_RESP, ABORTED, ERROR}
明确排除（降低复杂度）：backpressure, interrupt, burst, alignment, clock gating

12.2 验收标准（必须全部满足）

#验收项判定标准
1Feature 提取从 Spec 提取 5 个 Feature，人工确认后入库
2Structural 分析自动提取 FSM、writer 图、COI，与人工审计一致率 >80%
3Interaction 生成自动产生 ≥10 个有意义 Interaction，无人工干预
4Scenario 生成自动产生 ≥30 个 candidate scenario，Validity Engine 排除 <50%
5Ranking 工作Explorer 每轮选出 Top-5，按 Priority 排序
6Cocotb 执行每轮 batch 自动运行，产出结构化 result.json
7Oracle 判定至少 2 个 Oracle（Reference Model + Invariant）运行并产出 verdict
8状态更新执行结果自动更新 Scenario status（VERIFIED/FAILED/NOT_REACHED）
9闭环迭代运行 5 轮后，VERIFIED scenario 数量单调递增，UNKNOWN 数量单调递减
10Negative Space至少 3 个 scenario 被标记为 EXCLUDED 或 UNREACHABLE，有明确原因

12.4 成功标准

v0.1 的成功标准不是"发现了多少 bug"，而是"机器能否在没有人工指定 testcase 的情况下，自主生成 Scenario、自主排序、自主执行、自主判定、自主更新状态，并在 5 轮迭代后让 Unknown Critical Space 单调下降"。

13. 与 AIGV 1.0 的关系

AIGV 2.0 不是替代 AIGV 1.0，而是在其 Governance 框架上叠加 Intelligence、Execution、Judgment 三层引擎。

AIGV 1.0（框架层）AIGV 2.0（引擎层）
数据模型（REQ → VI → SCN → TEST → EVIDENCE）Verification Space Builder 自动产生 SCN
状态机（DISCOVERED → ... → VERIFIED）状态转换由工具执行结果自动驱动
Coverage Hole 分类（C1-C6）C1/C2 由 Formal/Validity Engine 自动关闭；C3 由 Explorer 自动发现
文档体系（10 份文档）自动快照 + 机器生成报告，人工只审 final sign-off
证据闭环（到达 + 裁决 + 证据）Multi-Oracle 自动裁决，Evidence 自动落盘
人工审查每个 VERIFIED分层审查：L0 自动 / L1 抽样 / L2 强制 / L3 升级
兼容性保证：AIGV 2.0 的所有输出（Scenario、Evidence、Judgment）均符合 AIGV 1.0 的追踪主链格式，可无缝接入现有文档体系和签核流程。
