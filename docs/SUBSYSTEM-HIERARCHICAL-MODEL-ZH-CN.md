# MoonGlass 复杂子系统层次化开发模型

> 状态：评审稿 · 供评审
> 日期：2026-10-05
> 关联版本：v1.1.0 基线之后
> 前置文档：`docs/AIGV-TOP-FIRST-STRATEGY-ZH-CN.md`、`docs/VERIF-RUN-LOOP-DESIGN-ZH-CN.md`、`reports/changes-2026-10-05.md`
> 结论先行：复杂子系统（/简单 SoC）开发的四个痛点（子模块无设计文档、RTL 无法分派并行、
> 既有代码无法登记复用、子模块验证与子系统验证无差异化管理）是同一件事——
> **领域模型缺"子模块"这个一等实体**。本设计引入中心载体 **模块注册表（module registry）**，
> 由 ARCH 阶段产出并冻结，驱动 RTL 并行派发、复用登记与差异化验证。
> TOP 优先策略不推翻：签核链条仍在子系统顶层闭合；子模块 UT 的角色从"签核层"变为"并行开发准入层"。

---

## 1. 背景与问题（用户需求 2026-10-05）

以 MoonGlass_HSM 这类复杂子系统为例：

1. **子模块无设计文档**：REQ_SPEC 面向子系统整体，ARCH 只产顶层架构三件套（architecture/microarchitecture/clock_reset），子模块没有详细设计文档，RTL 会话拿到的上下文不足。
2. **RTL 无法分派并行**：RTL 阶段目前是单会话推进；用户希望不同子模块分给不同会话单独实现。
3. **既有代码无法登记复用**：某些子模块已有确定可用的代码（非 MoonGlass 标准产出），无法指定"这几个模块就用这份代码"。
4. **验证无差异化管理**：新开发子模块应单独完成**轻量 UT**（主要基本功能 pass 即可），其余交给 IT/ST 详细用例覆盖；现行体系没有"模块级轻量验证"与"子系统级严格验证"的分层。

## 2. 总判断与中心载体

四个问题共用同一个解：**ARCH 阶段产出机器可读的模块注册表**，作为后续三个阶段的事实源：

```
ARCH：分解子系统 → 模块注册表（+ 每模块设计文档/适配说明）
  ↓ 驱动
RTL：按依赖波次分派模块会话并行实现（复用模块直接采用，不写）
  ↓ 驱动
VERIF：按 verifyTier 差异化验证（UT_BASIC 轻量 / REUSED_VERIFIED 免验 / TOP_SIGNOFF 全量）
  ↓ 驱动
QA：按 tier 分别审计 + 复用模块 provenance/许可证核查
```

设计不变量（延续既有哲学）：

- **注册表条目必须锚定真实**：模块名在结构模型中存在（幻觉条目引擎拒绝）；复用文件哈希登记后变动可检测。
- **签核链条只在顶层闭合**：UT 证据进证据区但标注 tier，不进签核闭环分母（沿用 TOP 优先策略口径）。
- **写权纪律工具化**：模块所有权守卫与 rtl-write-guard 同一"尽力拦截 + 落盘审计"哲学，不靠提示词自觉。

## 3. 模块注册表 Schema

落盘 `docs/03_design/module-registry.json`（ARCH 冻结，经工具登记/更新，Agent 禁手改细节走 adjudication 口径）：

```ts
{
  version: 1,
  generatedAt: string,
  subsystem: string,                 // 子系统名 = 顶层模块名
  modules: [{
    name: string,                    // RTL 模块名（锚点校验：结构模型中必须存在）
    role: string,                    // 一句话职责（≤80 字）
    designDoc: string | null,        // docs/03_design/modules/<name>.md；reuse 模块为适配说明
    source:
      | { kind: 'new' }
      | { kind: 'reuse', origin: string, files: string[], hash: string, license: string | null, provenance: string }
      | { kind: 'ip-template', libraryId: string, templateId: string },
    verifyTier: 'UT_BASIC' | 'REUSED_VERIFIED' | 'COVERED_BY_TOP',  // 默认 COVERED_BY_TOP
    owner: string | null,            // RTL 属主会话名（派发时回填）
    dependsOn: string[],             // 依赖模块（波次排序依据）
    interfaces: string[]             // 关联架构契约/接口 ID
  }],
  integrationOrder: string[][]       // 波次：每波内可并行，波间串行
}
```

配套：`docs/03_design/modules/<module>.md` 标准模板（职责/接口契约/内部结构与状态机/寄存器/边界与异常/验证要点）。**新建模块写全篇；复用模块只写适配说明**（接口差异、包壳需求、已知限制）。

## 4. 各阶段改造

### 4.1 REQ_SPEC
- 不变为主；规格条款增加**模块归属映射**的约定（条款与模块责任矩阵挂钩，供 VERIF 条款闭环归属到模块、供变更影响分析）。

### 4.2 ARCH（改动最大）
- 新增任务：子系统分解 → 模块注册表 + 每模块设计文档/适配说明；接口契约冻结（总线/寄存器块/模块间接口的权威定义，后续模块会话的唯一依据）。
- **ARCH→RTL 门禁新增**：注册表完备性（每个架构模块有条目；新模块有设计文档；复用模块有适配说明+provenance；integrationOrder 无循环依赖）。

### 4.3 RTL（见 §6 并行编排）
- 模块会话按波次派发；复用模块不写代码只登记；顶层集成为单独收尾会话。
- **RTL→VERIF 门禁新增**：复用模块 provenance 完整（origin/hash/license）；lint 口径分层（§7.3）。

### 4.4 VERIF（见 §5 差异化验证）
- 运行循环波段扩展：W0 规划 → **W-UT 模块波**（并行跑 UT_BASIC 模块的轻量 UT）→ W1 条款 → W2 corner×配置点 → W3 签核。UT 波只覆盖 `verifyTier=UT_BASIC` 模块；其余波段不变（TOP 口径）。
- 回流规则：**IT/ST 暴露的模块级缺陷，回该模块补 UT 用例**（下次同类问题 UT 拦截）；UT 豁免的覆盖面必须在 TOP 场景条款映射中有对应，不留两不管地带。

### 4.5 QA
- 按 tier 分别审计：UT_BASIC 看基本用例 pass + lint；REUSED_VERIFIED 看 provenance/许可证/哈希未漂移；TOP_SIGNOFF 看现行全套。
- 完备性审计扩展：注册表内模块的 tier 覆盖声明齐全。

### 4.6 SYNTH
- 子系统综合报告按模块分解面积/时序（模块维度本来就在层级里）；复用宏模块的 PPA 口径沿用架构文档假设条款。

## 5. 差异化验证三层模型

| 层级 | 对象 | 完成判据 | 签核关系 |
|---|---|---|---|
| `UT_BASIC` | 新开发且注册表声明需 UT 的子模块 | 基本功能用例（happy path + 1-2 个关键边界）PASS + lint 零 error；不做覆盖率门槛/Mutation/Multi-Oracle | 证据登记并标注 tier，不进签核闭环分母 |
| `REUSED_VERIFIED` | 复用模块 | 免 UT 或仅冒烟；理由 = provenance 登记（来源/版本/历史验证证据） | 不进签核分母 |
| `COVERED_BY_TOP` | 其余子模块 | 不单独验证，由子系统 IT/ST 覆盖 | 顶层条款闭环覆盖 |
| `TOP_SIGNOFF` | 子系统顶层 | 现行 AIGV 全套（条款闭环/配置覆盖/证据审查/门禁） | **签核在此闭合** |

与既有机制的关系：
- `UT_EXCEPTION`（诊断驱动的例外深挖）**保留不变**——那是调试通道；`UT_BASIC` 是计划内的轻量通道，两者并存。
- 引擎 `module-verification-strategy` 的分级改为**注册表优先**：顶层恒 TOP_SIGNOFF；注册表内模块按其 `verifyTier`；未登记模块 COVERED_BY_TOP。现行结构推导（风险分）降级为"建议是否该给某模块开 UT_BASIC"的提示输入。
- UT 环境沿用 `verification/<module>_tb` 目录惯例与 cocotb 技能；UT 结果落 `verification/results/<module>/`（现有证据区粒度天然契合）。

## 6. RTL 并行开发编排

### 6.1 波次派发
- 按 `integrationOrder` 波次串行、波内并行；**波内并行会话上限默认 3**（token 与冲突面考量，可调）。
- 每模块一个任务会话（startTask，parentSession 血缘到 RTL 主会话），prompt 携带：该模块设计文档 + 冻结接口契约 + 允许写的文件集合 + UT_BASIC 要求（若该 tier）。
- **共享文件纪律**：顶层、filelist.f、design.json、寄存器块只归集成会话写；模块会话越界写由"模块所有权守卫"拦截（rtl-write-guard 升级为按会话授权文件集合；尽力拦截 + 落盘审计，同既有哲学）。
- 模块完成判据：编译 + lint 过 +（UT_BASIC 则）基本用例 pass → 登记完成 → 波次推进；集成会话做顶层连线 + 全设计 lint/elaboration。

### 6.2 接口变更
- 中途改契约走变更单；受影响模块的属主会话都收到变更通知（沿用 phase changeNotice 的机制下沉到模块粒度）。

### 6.3 已知边界（诚实声明）
- 并行会话同时跑仿真会撞构建目录 → tb/build 目录按模块隔离（cocotb 环境本来就按模块分目录）。
- 模块会话的上下文只带该模块索引（产物索引按模块裁剪，避免子系统规模下索引本身膨胀）。
- 模块会话反复修不好某模块 → 升级通道：LLM 决策层提案（换实现思路/简化规格/转人工），沿用 VERIF-RUN-LOOP 的决策账本。

## 7. 复用通道（指定代码登记）

1. **登记**：注册表 `source.kind='reuse'`，代码复制进 `rtl/` 并记哈希；来源可以是本地路径或 IP 库条目（IP 库模板经 `ip_inspect` 引用时自动带出 provenance）。
2. **写保护**：RTL 阶段该模块文件对一切会话只读；接口不符只准写 wrapper（wrapper 是新代码，走新开发流程）。
3. **lint 口径（建议默认）**：复用模块 lint **error 仍阻断、warning 降级为记录**——error 多对应真实缺陷/不可综合，全免会失去底线；warning 噪音（风格类）不该挡住"已被硅证明的代码"。
4. **回流检测**：哈希变化 → 提示"上游代码已更新，是否回流"（QA 也会核哈希未漂移）。
5. **许可证**：license 字段必填（可空但需明示"内部资产"），QA 门禁核查。

## 8. 与既有机制的关系（不推翻清单）

| 既有机制 | 关系 |
|---|---|
| TOP 优先策略 | 不推翻：签核闭合点仍在顶层；UT 从签核层变为开发准入层 |
| `UT_EXCEPTION` | 保留：诊断驱动深挖通道，与计划内 UT_BASIC 并存 |
| IP 智能库 | 不变：模板生成通道；reuse 通道是"原样采用"，两者互补 |
| 验证运行循环 | 波段扩展 W-UT；批次聚类（模块维度已有）沿用；子系统默认预算放宽（§12） |
| 漂移对账/阶段重置 | 阶段级不变；模块级"重做某子模块"见 §9-A |

## 9. 牵连面全景（"还会有哪些牵扯"）

按组列出，实施时逐组评估：

**A. 流程与门禁**
- 阶段门禁新增项（§4.2/4.3）；模块级阶段重置（"只重做某子模块"：漂移对账目前按阶段目录映射，需要模块粒度扩展或明确"只支持到阶段"）；变更单影响面分析按模块归属传播。

**B. 会话与上下文**
- 模块会话的生命周期跨阶段（RTL 写的模块，VERIF 修 bug 时上下文怎么带：模块设计文档 + 该模块证据摘要注入，而不是全项目历史）；
- 模块级 `.pi/APPEND_SYSTEM.md` 产物索引裁剪；模块会话中断续跑；并行会话数与循环 token 预算的联动（并行 3 会话 = 3 倍燃烧率，预算默认值要相应放大）。

**C. 引擎与证据**
- 注册表↔结构模型对账（模块名锚点校验）；需求条款↔模块映射进规格映射矩阵（条款闭环可归属到模块）；风险寄存器的 `risk.object` 与注册表联动（注册表外对象的风险单独列出）；
- `verification/results/<module>/` 与 `verification/<module>_tb/` 目录惯例固化；config-space 按"顶层寄存器 vs 模块内部寄存器"分层（子系统寄存器手册规模会大一个量级，抽取与覆盖矩阵都要分块）。

**D. IP 与资产**
- IP 库模板作为 reuse 来源（provenance 自动带出）；复用代码上游更新的回流检测（哈希比对）；许可证扫描进 QA。

**E. 项目与呈现**
- ChipProject 数据模型加子系统标记/规模；外部工程导入识别模块结构预填注册表初稿；Dashboard/项目总览加模块维度进度；需要一个示例子系统项目作为模板与回归夹具。

**F. 文档与交付**
- doc-repository 追溯检查器纳入模块设计文档（MG-DOC 检查项扩展）；签核包按模块层级组织证据索引；用户手册/白皮书补层次化章节。

**G. 失败与例外路径**
- 模块开发失败的降级决策通道（换实现/简化规格/转人工，走决策账本）；
- IT/ST 失败回流到模块 UT 的规则执行点（修复会话派发给模块属主会话还是 VERIF 会话——建议：修复仍在 VERIF 会话/修复会话，但根因记录标注模块归属，回流动作进决策层）。

**H. 长程循环**
- W-UT 波的并行 UT 派发复用批次编排（场景聚类已是模块粒度）；UT 波的熔断口径比 TOP 波松（基本用例挂了就熔断修，不做诊断升级五层账本）。

## 10. 实施分批

1. **批 1｜注册表与 ARCH**：schema + 引擎锚点校验 + ARCH 任务与门禁 + 模块设计文档模板 + doc-repository 追溯纳入。
2. **批 2｜RTL 并行派发**：波次编排 + 任务会话模板 + 所有权守卫 + 模块级索引裁剪。
3. **批 3｜复用通道**：reuse 登记 + provenance/哈希 + 写保护 + lint 分层 + 许可证核查。
4. **批 4｜差异化验证**：三层 tier 进引擎策略（注册表优先）+ UT_BASIC 轻门槛与回流规则 + 运行循环 W-UT 波。
5. **批 5｜QA/SYNTH/呈现**：分层审计 + 综合模块分解 + Dashboard 模块维度 + 手册/白皮书 + 示例子系统项目。

每批交付口径沿用既有规范：typecheck 全过、对应 smoke 随批交付、引擎包零新依赖。

## 11. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 注册表与真实 RTL 漂移（模块改名/合并） | 锚点校验进门禁；rebuild 时对账列出漂移项待人处理 |
| 并行会话写冲突 | 所有权守卫 + 波次串行点（共享文件只归集成会话）+ 审计落盘 |
| 差异化验证被误读为"质量放水" | UT_BASIC 判据写死底线；UT 豁免的覆盖面必须挂 TOP 条款映射；QA 按 tier 审计 |
| 子系统上下文/token 规模爆涨 | 模块级索引裁剪 + 并行上限 + 预算按规模分档 |
| 复用代码带病 | lint error 不豁免 + 冒烟用例 + provenance 与哈希漂移检测 |

## 12. 待决策问题（建议默认值，评审确认）

1. **注册表形态**：`module-registry.json` + `modules/*.md` 双载体（机器可读 + 人读）——建议采纳；纯 markdown 解析方案不推荐（上一轮解析内核重写刚证明自由文本解析的代价）。
2. **UT_BASIC 底线**：happy path + 1-2 个关键边界 + lint 零 error——建议采纳为默认；不够可在评审中加。
3. **复用模块 lint 口径**：error 阻断、warning 降级记录——建议采纳；不接受"全免"（失去可综合性兜底）。
4. **并行会话上限**：默认 3，可调到 4——建议采纳；与 token 预算联动（子系统项目循环默认预算放宽一档：步数 80 / token 15M / 墙钟 480min，待实测校准）。
