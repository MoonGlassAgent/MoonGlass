摘要

大语言模型已经能够生成具有一定复杂度的 RTL、测试代码和设计文档，但“能生成代码”与“能交付 ASIC IP”之间仍存在显著距离。真实芯片工程要求需求可追踪、架构决策可解释、RTL 可综合、验证可复现、变更可传播、质量门禁可核验，并要求工具失败、模型漂移与人工决策能够在统一流程中被控制。本文基于 MoonGlass ASIC Design Agent 的持续开发实践，归纳需求与规格融合、非线性阶段推进、Agent 会话隔离、验证证据独立审查、双通道覆盖率、已有工程接续、IP 库语义索引、SRAM 多视图建模、Windows 开源 EDA 工具链兼容等问题。

本文提出一种证据驱动型人机协同 Agent 工作流：以确定性状态机管理项目阶段，以结构化追溯矩阵连接需求、规格、设计、测试和签核证据；以主 Agent 承担端到端交付，以独立 Review 读取原始工程产物；以 Cocotb + Icarus 承担功能回归，以 Verilator 承担 RTL 覆盖率签核；以事件、日志、JUnit、覆盖率和综合报告构成可核验证据链。文章进一步给出评价指标、有效性威胁和开放研究议程，为开源社区讨论“如何从 AI 辅助编码走向可控芯片工程交付”提供一个可检验框架。

关键词：ASIC IP；RTL；Coding Agent；人机协同；设计验证；覆盖率；需求追溯；质量门禁；开源 EDA；证据驱动工程

1. 引言

芯片开发 Agent 面临的首要问题并不是“如何写出更多 RTL”，而是“如何证明生成结果满足需求，并能在变更、回归和签核中持续成立”。

通用 Coding Agent 的交互范式通常是：用户描述任务，模型读取代码，调用工具，修改文件并返回总结。这一范式对软件仓库十分有效，但 ASIC IP 开发增加了若干强约束：行为必须与周期、复位、协议和异常语义一致；RTL 必须通过编译、Lint、仿真和综合；设计与验证资产需要跨阶段追踪；工艺库、存储器宏和第三方 IP 具有多视图与授权约束；后期需求变更会触发架构、RTL、验证、质量和综合的级联响应。

如果系统只优化代码生成质量，容易出现四种“虚假完成”：第一，Agent 声称功能完成，但没有原始日志与回归结果；第二，仿真通过，但测试没有有效检查点；第三，覆盖率较高，但需求和异常场景没有对应测试；第四，前序规格已经变化，后序结果仍显示完成。MoonGlass 的开发过程反复遇到这些问题，并由此逐步从“流程看板 + 对话”演化为“状态控制 + 工具执行 + 证据审查”的工程系统。

核心立场：ASIC Agent 的完成条件不应由自然语言总结定义，而应由可追踪需求、可复现工具运行、结构化质量门禁和人工签核共同定义。

1.1 本文贡献

  1. 给出 ASIC IP Agent 开发中流程、控制、验证、复用、工具链和交互问题的系统分类。

4. 非线性六阶段流程与变更传播

4.1 需求与规格的协同形成

传统流程可以将需求定义与规格定义视作不同活动，但在 Agent 对话中，用户描述功能的同时往往会确定接口宽度、时序语义、异常行为和验收标准。强行分成两个阶段会产生重复对话和文档漂移。因此 MoonGlass 将两者合并为 REQ_SPEC，同时保留需求与规格的双向矩阵，使阶段合并不等于追溯关系消失。

REQ_SPEC 需求-规格定义 → ARCH 架构设计 → RTL RTL 开发 → VERIF 验证完备 → QA 质量检查 → SYNTH 综合实现

4.2 阶段状态不是文件夹状态

阶段完成不能只由目录或文件存在决定。一个可信阶段状态至少应包含：阶段产物、工具运行、门禁结果、变更响应、人工确认和时间戳。对于已有工程，还需要根据真实证据恢复阶段，而不是因为目录不符合 MoonGlass 模板就回到起点。

4.3 回退、修改与影响传播

用户可以双击进入任意阶段而不删除后续产物。只有当前序阶段发生实质修改，而且某个后序阶段此前已经完成时，后序阶段才出现影响提醒。该规则避免了“一推进后面全黄”的误报，也避免了“回看文档就破坏状态”的过度反应。

Impact(Pᵢ → Pⱼ) = Changed(Pᵢ) ∧ Completed(Pⱼ) ∧ (j > i)

影响响应可以采用两种路径：从变更起点重新托管到终点，或由用户逐阶段处理。规格变化通常要求架构影响分析、RTL 修改、验证回归、QA 变更审查和重新综合；Bug 修复则可能从 RTL 或 VERIF 开始。系统应保留旧证据，形成变更前后可比较的审计链。

4.4 条件性交付物

简单单时钟模块可能无需独立 clock_reset.md，小型组合或浅流水设计也未必需要专门的 microarchitecture.md。门禁应判断复杂度和风险，而不是把所有文件模板变成绝对要求。建议将交付物分为“必需、条件必需、推荐、可选”四级。

5. Agent 自主性、会话隔离与人工控制

5.1 主会话的端到端责任

用户未必创建平行会话，因此主 Agent 不能依赖“另一个 Agent 会替我 Review”。主会话应以最终交付为目标：理解需求、产生设计、调用工具、读取失败、修复问题、补齐验证、生成报告，并在无法完成时明确列出阻断证据。

5.2 平行会话不是弱化副本

平行会话应拥有独立模型、独立上下文和完整工具能力。它可以用于架构 Review、RTL Review、覆盖率补充、Bug 定位，也可以执行完全不同的探索任务。其价值取决于用户安排，不应被硬编码为单一“审查角色”。

5.3 模型选择和会话恢复

模型选择必须以项目和会话为键持久化。软件重启时不仅要恢复消息历史，还要恢复 Provider、模型 ID、活动会话和运行状态。界面显示必须以结构化会话状态为准，不能因为 Provider 列表加载较慢而显示“未选择模型”。

5.4 人工确认与批量决策

当 Agent 一轮提出多个决策时，任意一项确认都触发下一轮，会造成其余决策丢失。更合理的交互是：记录每项选择，全部完成后一次提交。托管模式则可以根据预设政策自动选择推荐项，但关键风险项仍应中断或形成显式豁免。

5.5 中止语义

中止需要跨越四层：UI 状态、Agent RPC、模型请求和 EDA 子进程树。仅取消前端等待会造成“按钮显示停止但后台仍执行”。可靠实现应传播取消信号、回收进程、清空等待者，并保留已完成工具证据。

6. 从仿真通过到验证证据闭环

6.1 四个不等价命题

必须区分：编译成功 ≠ 仿真通过；仿真通过 ≠ 覆盖充分；覆盖充分 ≠ 需求已验证；需求已验证 ≠ IP 已具备流片签核条件。

Agent 容易把工具的局部成功概括成整体完成。为抑制这种偏差，验证状态需要直接读取机器可读结果，而不是解析自然语言总结。每个模块至少需要测试总数、通过数、失败数、跳过数、退出码、JUnit、日志、波形和覆盖率。

6.2 Windows 双通道验证架构

MoonGlass 当前采用双通道方案。Cocotb + Icarus 用于 Python 驱动的功能回归、参考模型检查和功能覆盖率；Verilator C++ 回归用于 RTL 行、条件或表达式、翻转和 FSM 覆盖率。这样绕开 Windows 环境中 Cocotb-Verilator VPI 组合的库与 wrapper 限制，同时保留两类证据。

6.3 建议覆盖率门限

MoonGlass 当前把行覆盖率 90%、条件或表达式覆盖率 85%、功能覆盖率 80% 作为基础门限。这些数值是工程默认值，不是普遍适用的行业签核标准。复杂控制器、安全模块或高可靠场景需要更严格目标；不可达代码、第三方黑盒和防御性分支则需要有理由的豁免。

证据回答的问题主要盲点
行覆盖率哪些可执行 RTL 被运行过运行不等于结果被检查
条件/表达式覆盖率逻辑真假组合是否被激活未证明端到端需求
翻转覆盖率位级活动是否出现无语义保证，数据总线容易虚高
FSM 覆盖率状态与迁移是否被访问状态编码识别和不可达迁移
功能覆盖率规格场景、边界和交叉组合是否命中覆盖模型本身可能遗漏需求
断言协议和时序不变量是否保持断言完整性与 vacuity

6.4 独立证据 Review

Review 不接受主 Agent 的“验证完成”结论，而是重新读取测试源码、原始结果、JUnit、编译日志、仿真日志和覆盖率。确定性审查器检查：是否存在有效测试数量、是否有跳过测试、是否存在断言或 Scoreboard、覆盖率是否达标、两条通道的证据路径是否存在且非空。

这一机制仍不是完整的模型独立审查。后续可以让另一模型在确定性审查结果之上，对需求遗漏、弱检查点、参考模型同源错误和覆盖模型缺口进行语义 Review。但第二模型也必须引用原始证据，不能只评价主 Agent 的总结。

7. 追溯矩阵、门禁语义与质量控制

7.1 追溯矩阵的角色

追溯矩阵应连接 REQ、SPEC、设计项、测试项和质量证据，使系统能够回答：某条需求在哪里实现、由哪些测试验证、当前证据是否有效、变更后哪些结果需要重跑。矩阵不是为了增加文档数量，而是为了支持影响分析和签核解释。

7.2 定义与引用必须分离

版本历史、优先级说明和 TBD 表可能引用需求 ID，但它们不是正式映射行。若校验器只用正则扫描所有表格，就会把辅助内容误判为缺少规格映射。正确方法是识别规范表头、展开范围 ID、验证状态值，并忽略模板和后续阶段尚未生效的文档。

7.3 门禁应具备五态语义

状态含义推进策略
通过证据满足要求允许推进
警告存在风险但不构成当前阻断记录后推进
条件通过满足条件或存在受控限制需责任人确认
阻断关键证据缺失或工具失败修复后重试
不适用经复杂度和场景判断无需执行记录理由

一键托管模式下，需求和架构早期的格式类门禁可以转为自动修复或延后审查，避免频繁中断；但 RTL 编译失败、测试失败、覆盖率严重不足和综合失败仍应阻断。强制推进必须形成显式事件，而不是静默改绿。

8. IP 库发现、语义增强与 SRAM 多视图建模

8.1 从目录导入到可检索资产

用户可能只提供一个包含数十个 IP 的根目录。确定性扫描器应递归识别 RTL、Top、模块、测试、VIP、BFM、文档和清单，生成结构化索引；Pi 只负责补充协议角色、用途、参数含义、适用场景和置信度。这样即使语义分析返回截断 JSON 或 Agent 正忙，基础索引仍可用。

8.2 复用决策需要多因素检查

架构和 RTL 阶段可以优先搜索 IP 库，但不得强制使用不符合需求的模板。候选 IP 至少需要检查接口协议、参数范围、时钟复位、异常语义、验证状态、许可证和工艺视图。验证阶段还可复用 AXI Master VIP、AXI Slave VIP 等组件，但应防止测试环境与 DUT 共享同源缺陷。

8.3 SRAM 不是单一 Verilog 文件

项目希望的逻辑尺寸常由 Wrapper 暴露，内部实例化实际可生成的 Macro。一个可靠 SRAM 资产应同时描述：项目 Wrapper、仿真行为模型、综合 Blackbox、Liberty、LEF/GDS 和生成参数。若仅生成通用寄存器数组，功能仿真可能通过，但面积、时序和低功耗语义没有工艺意义。

Architecture size request → SRAM wrapper (logical interface and polarity) → foundry macro instance (available physical size) ├─ simulation model ├─ synthesis blackbox ├─ Liberty timing/power └─ LEF/GDS physical views

9. 开源 EDA 工具链的可执行性工程

9.1 安装成功不是可用成功

工具安装后可能没有刷新 PATH，或者受到冲突 DLL、缺失编译器、Perl wrapper、Make 名称和文件格式支持的影响。因此每个工具需要四级状态：已配置、已发现、最小自检通过、项目任务通过。环境检测结果应缓存，并在路径变化、版本变化或用户主动刷新时重新执行。

9.2 Windows 特有问题

  • Icarus 可能受其他 MinGW DLL 污染，需要隔离运行环境并执行最小编译与 vvp 自检。
  • Verilator Windows 包可能提供 verilator_bin.exe 而非预期 Perl wrapper，并依赖外部 g++ 与 Make。
  • GTKWave 能启动 GUI 不代表指定 FST 能打开，需检查版本、格式、路径与退出码。
  • 工具输出中的 D:\... 必须被识别为完整绝对路径，不能漏掉盘符。

9.3 工具输出的结构化

Agent 工具不应只返回长文本。推荐同时返回状态、退出码、时间、文件路径、诊断数组和可点击位置。大输出应保存到文件并在界面标记“截断”，避免用户误以为文件内容本身不完整。

10.2 证据对象模型

每项关键结论都应关联证据对象。证据对象至少包括：产生者、工具与版本、命令或参数、输入哈希、输出路径、退出状态、时间、适用阶段和关联需求。这样才能判断证据是否因 RTL、测试、约束或工具版本变化而失效。

11. 可复现实验与评价指标

要把工程经验推进为学术研究，需要建立公开基准任务和对照实验。可选任务包括 APB 寄存器块、异步 FIFO、AXI-Lite Bridge、DMA 子模块、时钟分频器和带 SRAM Wrapper 的控制器。每个任务提供冻结需求、隐藏缺陷、参考测试和预期综合边界。

11.1 建议对照组

  1. 仅聊天模型，不允许工具调用。
  2. 通用 Coding Agent，可修改仓库但无阶段和门禁。
  3. MoonGlass 主会话，无独立证据 Review。
  4. MoonGlass 完整流程，含证据 Review 和覆盖率门禁。
  5. 资深工程师传统流程，作为时间与质量参考而非绝对真值。

11.2 消融实验

可以分别移除追溯矩阵、功能覆盖率、RTL 覆盖率、独立 Review、阶段变更传播或平行模型 Review，观察缺陷逃逸、误报、时间和 Token 成本变化。该设计有助于回答“复杂流程机制是否真正提高质量，还是只增加形式负担”。

12. 有效性威胁与当前局限

12.1 内部有效性

MoonGlass 与测试项目共同演进，部分改进可能针对已知案例过拟合。Agent 模型、Prompt 和工具版本变化也可能影响结果。需要固定版本、保存运行记录并使用隐藏测试。

12.2 外部有效性

中小型数字 IP 的经验不能直接泛化到大型 SoC、模拟混合信号、NoC、GPU、复杂一致性协议或安全认证项目。Windows 开源工具链的结论也不能代表 Linux 和商业 EDA 环境。

12.3 构念有效性

覆盖率和门禁通过只是验证完备性的代理指标。高覆盖率可能由弱测试产生，追溯矩阵也可能形式完整但语义错误。因此必须引入缺陷注入、变异测试、隐藏场景和专家 Review。

12.4 结论有效性

当前尚无大样本统计，本文的“有效”主要指工程功能已经运行，而非已经证明优于其他方法。公开论文版本应报告样本数量、置信区间、失败案例和负面结果。

重要限制：当前 MoonGlass 的证据 Review 以确定性审查为基础，能够发现证据缺失和门限不足，但还不能证明参考模型正确、断言无 vacuity、CDC/RDC 安全、低功耗语义正确或时序已经达到商业签核标准。

13. 开放研究议程

  1. 语义级需求覆盖：如何判断测试真正验证了需求，而不是仅在文件中引用了同一 ID？
  2. 独立 Review 的独立性：不同模型、不同 Prompt、不同工具证据如何降低同源错误？
  3. 变异测试驱动的测试质量：通过自动注入 RTL 缺陷，衡量 Agent 生成测试的故障检出能力。
  4. 形式验证协同：自动从规格生成属性，使用 SymbiYosys 等工具验证控制不变量和边界条件。
  5. CDC/RDC 与低功耗：将结构检查、UPF 意图和跨域协议纳入阶段门禁。
  6. 覆盖率闭环策略：如何避免 Agent 为追求数字而生成无价值激励或不可维护测试？
  7. 证据新鲜度：文件、参数、工具或模型变化后，哪些旧证据应自动失效？
  8. 工艺感知生成：如何将真实 Liberty、SRAM Compiler 和物理约束纳入架构选择？
  9. 安全与隐私：如何防止 API Key、专有 RTL、工艺库和客户需求进入不受控模型上下文？
  10. 可移植性：如何在 Windows 桌面、Linux 工作站和服务器多租户环境中保持一致工具语义？

14. 面向开源社区的讨论问题

  • 对不同类型 IP，哪些文件和门禁应当是必需、条件必需或可选？
  • 覆盖率门限应该由组织统一规定，还是根据模块风险动态生成？
  • 独立 Review Agent 是否必须使用不同模型，还是不同上下文与证据输入已经足够？
  • 如何设计公开、合法且具有代表性的 RTL Agent 基准，避免只测玩具模块？
  • Agent 自动豁免哪些问题是可以接受的？哪些必须由具名工程师确认？
  • 需求、RTL、验证和综合证据应采用怎样的开放数据格式，才能跨工具迁移？
  • 对于商业 EDA，MoonGlass 应只做编排层，还是需要统一诊断与结果模型？
  • 开源社区应如何记录失败案例，避免只发布成功 Demo 所造成的选择偏差？

15. 结论

MoonGlass 的迭代表明，把大语言模型放进 ASIC IP 开发流程后，最困难的问题会从“生成语法正确的 RTL”迅速转向“管理状态、变化、工具和证据”。需求与规格需要协同形成但保持追溯；阶段需要允许回访但准确传播影响；主 Agent 需要具备端到端能力，但不能自我签核；验证需要同时关注功能场景、RTL 结构和测试有效性；IP 与 SRAM 需要多视图；工具链需要用最小自检证明真实可用。

因此，可信 ASIC Agent 更接近一个由 Agent 驱动的工程操作系统，而不是嵌入聊天框的代码生成器。它应当把概率性推理用于理解、设计和调试，把确定性程序用于扫描、执行、状态和门禁，把原始工程证据用于 Review，把最终风险决策留给能够承担责任的人。

最终命题：芯片开发中的 Agent 自主性，不应以减少用户点击次数衡量，而应以在更少人工操作下仍保持需求可追踪、工具可复现、变更可响应和结论可审计的能力衡量。
