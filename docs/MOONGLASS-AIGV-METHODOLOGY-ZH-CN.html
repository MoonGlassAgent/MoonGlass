摘要

传统 RTL 验证计划通常从规格人工分解测试点，再由验证工程师构造环境、用例、覆盖模型和签核报告。Coding Agent 能够显著加速这些活动，但也引入新的可信性问题：模型可能把分类标签当作验证目标，把“测试运行”误写成“验证完成”，把高覆盖率误解为需求闭环，并可能在缺乏原始证据时生成乐观结论。

MoonGlass AIGV（AI-Guided Verification）提出一种语义化、风险驱动、证据闭环的方法：以规格事实与 RTL 结构事实为确定性基础，构建 Feature Interaction Graph 和结构风险标记；将风险转化为可证伪的 Verification Intent；把 Intent 展开为具有时间关系、边界条件、定向激励、观察点、Checker 和通过准则的 Scenario；利用仿真、Assertion、开源 Formal、静态分析和覆盖率反馈形成迭代闭环；将未闭环目标分类为 C1-C6 Coverage Hole，并要求每项缺口给出明确关闭证据。

AIGV 2.0 在此基础上引入五维 Verification Space、模块分层验证策略、六轴 Scenario 状态、Multi-Oracle 独立裁决、可审计 Explorer、经验性 Novelty Saturation、风险加权 Mutation 和 Residual Risk Register。系统不把“所有测试 PASS”或单个 passed=true 当作充分条件，而要求关键 Scenario 获得不同独立性域的有效裁决，并通过主动缺陷注入检验验证体系本身是否具备足够敏感性。

该方法不以 Agent 的自然语言结论作为签核依据，而以 REQ/SPEC → VI → SCN → TEST/COVER/PROPERTY → EVIDENCE → SIGNOFF 为统一追踪主链。工程执行被划分为验证规划、环境搭建、基础回归和风险闭环四个具有明确停止边界的交付步骤；当同一失败反复出现时，系统从直接修复切换到 L0-L5 渐进式诊断。最终输出是绑定规格、RTL Hash、Verification Space Snapshot、工具结果和残余风险的机器签核建议，最终批准仍由具名工程责任人完成。

本文给出其数据契约、算法逻辑、工程目录、工具分配、双层状态机、模块分层、探索停止条件、文档治理、签核准则、局限性与可复现实验方向。

1. 问题定义与方法目标

AIGV 要解决的不是“让 AI 多生成一些测试”，而是“让每个验证结论都能回答验证了什么、为什么验证、如何激励、观察哪里、怎样判定、证据何在”。

1.1 五类常见虚假完备

表面现象为何不充分AIGV 要求
所有测试 PASS测试可能没有有效 Checker，或从未到达关键状态同时证明场景到达、结果被裁决、原始证据可追踪
代码覆盖率很高执行到代码不等于验证其语义，异常交互可能仍缺失覆盖率绑定 Verification Intent 与 Scenario，而非孤立百分比
功能覆盖率 100%覆盖模型自身可能遗漏需求、边界和时间关系覆盖点必须由 REQ/SPEC、RTL 风险和 Intent 共同驱动
Agent 声称验证完成自然语言总结不可重复执行，也可能忽略失败日志独立读取 JUnit、result JSON、日志、波形、Coverage 和 Formal 结果
Risk 数量很多结构风险只是待验证假设，不等同于 RTL Bug通过 Scenario 和证据裁决为关闭、失败、不可达、豁免或规格阻断

1.2 方法目标

  1. 语义明确：任何 Risk、Intent 和 Hole 都应由工程师直接理解，而不是只显示内部 taxonomy。
  2. 可执行：Intent 必须可直接转化为 sequence、constraint、checker、property 和 coverage bin。
  3. 可证伪：目标必须允许出现反例，而非“验证模块工作正常”这类不可判定陈述。
  4. 可追踪：从需求到证据保持双向链接，变更后可以定位受影响验证资产。
  5. 可审计：结论依赖机器可读状态和原始产物，不依赖 Agent 自我声明。
  6. 可迭代：覆盖反馈、失败证据和 Formal 结果能够重新排序下一批验证任务。
非目标：AIGV 当前不替代商业仿真器签核、CDC/RDC 专用签核、低功耗验证、DFT、等价性检查和物理实现签核。开源 BMC 的有限深度 PASS 也不能被描述为数学证明。

2. 方法学基本原则

2.1 确定性事实与概率性推理分离

MoonGlass 将知识声明分为 SPEC_FACT、RTL_FACT、INFERENCE 和 UNKNOWN。需求 ID、RTL 寄存器写入关系、状态机和工具结果属于可引用事实；“某两个行为可能形成未测交互”属于推理；没有充分资料时必须保留 UNKNOWN，而不是由模型补齐。

类别来源允许用途禁止行为
SPEC_FACT已批准需求/规格及章节定义预期行为和环境合法性脱离原文改变外部语义
RTL_FACTAST、CFG、COI、寄存器写者、源码位置识别结构、控制和可观察对象把实现现状自动当作正确规格
INFERENCE规则引擎或 Agent 推理提出风险、假设和测试建议未经验证直接宣称 Bug
UNKNOWN缺失或矛盾信息形成 Spec Gap 或人工决策项静默猜测后继续签核

2.2 到达、裁决、证据三元闭环

Closed(Intent) = Reached(Scenario) ∧ Judged(Expected Behavior) ∧ Evidence Persisted

只有三项同时成立，Intent 才能闭环。波形显示场景发生但没有 Checker，只能记为 REACHED；Assertion 通过但 cover 目标不可达，不能证明真实功能；日志写着 PASS 但没有结构化结果和版本信息，也不足以签核。

2.3 风险标记不是缺陷结论

Risk Marker 表示“基于规格或 RTL 结构，有理由优先验证某种失效模式”。它可以最终被验证为安全、由 Formal 证明不可达、被规格澄清、被批准豁免，也可能暴露真实 Bug。界面和报告必须保持这种认识论边界。

2.4 覆盖率是反馈，不是终点

代码覆盖率说明结构被执行的程度；功能覆盖率说明预先定义的语义空间被采样的程度；Intent Closure 说明需求/风险目标是否具备到达、裁决和证据。三者互补，任何单项都不能代替其余两项。

3.1 确定性内核与 Agent 的职责

确定性内核Agent
扫描文档和 RTL；提取 ID、结构与工具结果；计算哈希；构建稳定 ID；分类状态；写原子 JSON；执行质量门禁。解释未知语义；提出有引用的验证假设；实现 sequence/checker/property；读取失败证据；修复 RTL 或环境；更新工程文档。

这一边界避免将整套方法退化成 Prompt Engineering。提示词负责规范 Agent 行为，但状态事实、文件产物、场景反馈和签核门禁由代码、结构化契约与真实工具执行共同实现。

4. 形式化数据模型

4.1 Requirement Model

Requirement Model 从 docs/02_requirements 与相关设计文档中抽取稳定的 REQ/SPEC ID、原始文本、优先级、语义特征及文件/行号。TBD、TODO、未定义和待确认项进入 unknown 集合，成为 Spec Gap 候选。

4.2 Structural Model

Structural Model 对 RTL Hash 绑定，包含结构事实、状态机、寄存器写入者、时钟复位域、时间依赖、控制流图、影响锥和协议结构。Slang AST 可用时优先使用 AST；无法使用时退回结构化 fallback，并显式记录 limitations。

4.3 Feature Interaction Graph

交互图节点包括 requirement、feature、RTL object、state、clock domain 和 scenario；边包括 READS、WRITES、CONTROLS、DEPENDS_ON、SHARES_STATE、PRECEDES、CROSSES_CLOCK、RECOVERS_FROM、COVERS 与 VERIFIED_BY。语义假设必须引用现有 Risk、RTL Object 和 Interaction Edge，防止 Agent 生成无结构依据的任意笛卡尔积。

4.4 Verification State Model

VerificationState v5 ├─ rtlHash / generatedAt / analyzer ├─ scenarios[] / statusCounts / criticalOpen[] ├─ verificationIntents[] │ ├─ objective / rationale / failureMode │ ├─ preconditions / stimulusProcedure │ ├─ observationPoints / expectedResults / passCriteria │ └─ boundaries / methods / evidence / status ├─ specGaps[] / coverageHoles[] ├─ regressions[] / formalResults[] ├─ interactionGraph / executionPlan / hypotheses ├─ verificationSpace / explorationRound / explorationHistory ├─ multiOracle / mutationAssessment / residualRiskRegister ├─ closureAssessment / signoffPackage ├─ moduleVerificationStrategy └─ structuralSummary

完整状态可较大，因此验证态势 UI 读取原子发布的紧凑快照 verification-posture.json；完整分析留在 verification-state.json。发布采用临时文件写入后原子重命名，避免 UI 在更新过程中读到半截 JSON。

4.5 Verification Space Snapshot

Verification Space 不是 Feature、Boundary、Interaction、Temporal 和 System State 的无条件笛卡尔积，而是由规格合法性、RTL 结构关系、协议规则、风险优先级和预算共同约束的有限候选集合。每个快照同时绑定 specHash、rtlHash 与候选 Scenario ID；输入不变时快照身份稳定，输入变化时旧探索结论自动失效。

4.6 Negative Space

“不执行”也是需要治理的工程结论。架构无效、协议非法、已证明不可达、规格未定义和超出当前预算的候选进入 Negative Space，并记录原因、证据与审批状态。未经批准的 Negative Space 不能被用来缩小签核分母；OVER_BUDGET 只表示延后，不表示关闭。

4.7 Scenario 六轴状态

单一状态枚举不足以表达真实验证进度。AIGV 2.0 将 Scenario 分解为生命周期、到达、裁决、证据、时效性和闭环六轴。一个场景可以已经 EXECUTED，却仍是 NOT_REACHED；可以得到 PASS，却因证据 PARTIAL 不能闭环；也可以在 RTL 变化后从 CURRENT 进入 IMPACT_UNKNOWN。状态不会因为重复重建模型而被“洗绿”，恢复 CURRENT 必须依赖绑定新 RTL Hash 的证据。

4.8 模块验证策略

层级适用对象验证深度
STATIC_ONLY低风险、结构简单的普通子模块编译/elaboration、Lint、可综合性、端口与未驱动检查
UNIT_SMOKE需要独立冒烟的普通子模块静态检查加最小合法事务、复位与基本 Checker
UNIT_FOCUSED结构或语义风险较高的子模块定向 Testbench、模块风险 Scenario、边界/异常/并发与 Oracle 证据
IP_SIGNOFFdesign.json 指定的顶层 IP完整 AIGV Intent/Scenario、端到端回归、Multi-Oracle、Mutation、Residual Risk 与签核包

风险分析仍覆盖全部 RTL，但只有顶层和风险选中的子模块进入完整 Scenario 闭环。验证深度由风险决定，Oracle 类型由语义决定；小模块可以在独立判断和定位收益明显时使用 Golden Model，顶层也不能为了形式完整而复制 RTL 作为“参考模型”。

5. 从 RTL 结构到可解释风险

5.1 风险语义契约

一个可用 Risk 不能只有 Error/Normal Collision。它至少应回答：

对象
风险位于哪个 module、register、state、protocol channel 或 clock domain？
条件
哪些事件在同周期、相邻周期、容量边界或恢复路径下发生交互？
失效模式
可能出现优先级错误、重复完成、漏完成、计数失配、状态残留还是数据撕裂？
外部影响
软件、上游/下游接口或系统能够观察到什么错误？
依据
命中了哪条结构规则、哪些 RTL Fact 和源码位置？置信度如何？

5.2 当前风险 taxonomy

ID风险类型典型失效优先方法
R01Event Collision / N-way Shared State并发事件优先级或共享状态更新次数错误定向仿真 + Assertion
R02Priority Dependency错误授权、请求饥饿、公平性失效Formal Candidate
R04Outstanding Dependency在途计数、完成归属或顺序错误仿真 + Scoreboard
R05Counter Boundary0/MAX 边界上溢、下溢或错误 wrapFormal + 边界仿真
R07/R11Error/Normal 与 Timeout/Late Response双重完成、迟到响应破坏状态时间交互仿真
R08Reset/Transaction Collision复位后残留 valid/busy 或重复完成仿真 + Assertion
R09/R16SW/HW Collision配置与硬件更新冲突、在途事务使用混合配置寄存器序列 + Checker
R10CDC Interaction脉冲丢失/重复、多比特撕裂静态 CDC + 定向仿真
R12/R13Backpressure / Resource Exhaustion数据丢失、覆盖、重复或队列越界长反压 + 容量边界
R15/R19Recovery / Interrupt Collision无法恢复、中断漏报/重复/无法清除Formal + 恢复序列

5.3 风险优先级

Priority = Criticality × RiskScore × Interaction × CoverageGap × Confidence × CostFactor

RiskScore 综合结构复杂度、交互强度、时间深度和并发性；Criticality 来自 P0/P1 需求；CoverageGap 在闭环后归零；Confidence 反映结构分析可信度；CostFactor 用于在预算内平衡 Static、Formal 与 Simulation。该公式用于任务排序，不应被解释为失效概率或安全完整性等级。

6. Verification Intent：从分类到可证伪语义

6.1 什么不是 Intent

“Error/Normal Collision: error × response” 只是 taxonomy 与 feature 的组合；“验证错误处理正确” 缺乏对象、激励、观察和判据；“覆盖异常场景” 无法直接执行。这些表述不能作为工程签核目标。

6.2 合格 Intent 的语法

推荐句式：验证【RTL/协议对象】在【明确前置状态】下，当【事件 A 与事件 B 按给定周期关系发生，并覆盖指定边界】时，【外部可见状态、响应、计数或数据】必须满足【规格定义的唯一结果】，且不得出现【具体失效模式】。

6.3 Intent 的七个必要部分

字段工程含义示例
objective可证伪的完整目标在 timeout 后到达 late response 时不得重复完成事务
preconditions场景起始状态存在一个 outstanding transaction，timeout counter=MAX-1
stimulusProcedure可执行的分步激励T0 发请求，Tn 触发 timeout，Tn+1/Tn+2 返回 response
boundaries必须遍历的边界outstanding=0/1/MAX-1/MAX，response offset=-2…+2
observationPoints信号、状态与 Checkerdone_valid、error、outstanding_count、scoreboard queue
passCriteria怎样算通过一次且仅一次完成；计数归零；无 assertion failure
evidence结论对应的原始产物scenario_hits.json、JUnit、coverage、log、必要波形

6.4 时间交互与边界空间

对两个关键事件 A、B，AIGV 至少考虑 BEFORE、SAME_CYCLE、AFTER 和 WITHIN_N_CYCLES；对计数器、FIFO、outstanding、长度和地址对象，考虑 0、1、MAX-1、MAX、overflow/wrap 等边界。这里不是无条件生成全组合，而是由结构关系、规格语义、风险优先级和执行预算筛选。

7. Scenario Registry 与执行计划

7.1 稳定场景身份

Scenario ID 由 taxonomy、RTL object 和稳定 feature 集合生成，使同一风险在重新分析后保持可追踪身份。场景状态包括 DISCOVERED、PLANNED、IMPLEMENTED、NOT_REACHED、REACHED、VERIFIED、FAILED、PARTIAL、WAIVED、BLOCKED_BY_SPEC、FORMAL_PROVED 与 FORMAL_UNREACHABLE。

7.2 执行计划字段

scenario-execution-plan.json 为每个候选场景保存 sequence、constraints、temporalConstraints、iterations、budgetSeconds、expected、checkers、priority 和 reason。Agent 应复用或实现指定 sequence，而不是只收到一句“补充异常测试”。

7.3 下一批选择策略

  1. 排除 VERIFIED、FORMAL_PROVED、FORMAL_UNREACHABLE 和已批准 WAIVED。
  2. P0 Scenario 是强制任务，不能因成本较高而长期饥饿。
  3. 优先 FAILED 与高 criticality、高 coverage gap 的场景。
  4. 将共享环境初始化或相同 protocol driver 的场景尽量合批。
  5. 默认每批最多三个 Scenario；遇到昂贵普通任务时继续寻找预算内候选，而不是提前停止。
  6. 每批结束后写 Scenario hit 和 Coverage Delta，再重建一次智能模型；批内不得反复全量重建。

7.4 反馈格式

{ "scenarios": [{ "id": "SCN-XXXXXXXX", "reached": true, "passed": true, "assertionPassed": true, "reachCount": 17, "coverageDelta": {"functional": 3.1, "line": 0.4}, "evidence": ["results.xml", "result.json", "wave.fst"] }] }

7.5 可审计探索与经验性饱和

Explorer 的每次真实选批形成一轮 exploration-history.json 记录，包含 Verification Space Snapshot、选中场景、预计成本、基线闭环集合、新增闭环和 novelty score。刷新页面或重建模型不算探索轮次。探索状态分为 NOT_ENOUGH_ROUNDS、PROGRESSING、EMPIRICALLY_SATURATED 与 STALLED。

停止语义：连续三轮没有语义新增，只能说明在当前 Verification Space、探索策略和预算下边际信息收益趋近于零，不能宣称数学完备。若关键 Scenario 仍开放，则状态是 STALLED，应增强空间模型、激励、Checker 或 Assertion，而不是继续重复相同批次。

8. Coverage Hole：从“数字没到”到“语义没闭环”

Coverage Hole 是一个具体 Intent/Scenario 未完成“到达 + 裁决 + 证据”的原因分类，而不是某个覆盖率百分比低于门槛的同义词。每个 Hole 必须携带 scenarioTitle、missingTarget、requiredStimulus、requiredObservation、closureEvidence、recommendedAction 和 confidence。

分类诊断语义正确处置错误处置
C1 UNREACHABLE目标在当前模型与 assumptions 下不可达审查 assumptions；保留 Formal 不可达证据或修正目标直接删除覆盖点
C2 CONSTRAINT BLOCKED验证环境约束阻断了合法场景检查协议合法性与过约束，最小化 constraint无条件放宽全部约束
C3 STIMULUS MISSING场景合法但当前 sequence 未产生目标交互生成明确时间关系和边界的定向激励只增加随机 seed
C4 OBSERVATION MISSING场景已经到达，但没有 Checker/Assertion 裁决增加观察点、scoreboard、assertion 或 cover把 reach 当作 pass
C5 SPEC UNDEFINED规格不足以定义唯一预期关闭 Spec Gap；必要时请求 L4 人工决策让 Agent 猜测预期
C6 TOOL/INSTRUMENTATION仿真、覆盖率、结果文件或插桩缺失/失败修复命令、环境和落盘链路后重跑用文字报告代替工具证据
关闭条件：“激励缺失”不能只改成“已补测试”。必须指出补了哪个 sequence、产生了什么时序关系、观察了哪些信号、Checker 如何裁决、Scenario hit 在哪里、覆盖率增量是多少、原始结果文件在哪里。

9. 多通道执行与证据闭环

9.1 功能通道

MoonGlass 以 Cocotb + Icarus 为当前主要功能验证通道。Cocotb 负责 Python sequence、driver、monitor、reference model、scoreboard 和结构化测试结果；Icarus 执行 Verilog/SystemVerilog 仿真。功能覆盖可由项目覆盖模型记录，并必须绑定 VI/SCN。

9.2 结构覆盖通道

Verilator 将 RTL 编译为 C++ 模型，并可插入 line、expression/branch、toggle、FSM 和 user coverage。MoonGlass 将该通道用于 RTL 结构覆盖率补强。代码覆盖率回答“哪些结构被执行”，但不独立回答“是否满足规格”。

9.3 静态与 Assertion 通道

Lint、可综合性检查、协议 assertion、局部不变量和结构规则为仿真提供低成本补充。Assertion PASS 需要同时确认 antecedent 真实发生，避免 vacuous pass；因此 assertion 与 cover/Scenario hit 应配对审查。

9.4 最小证据包

证据目的最低要求
result.json机器可读总体结果工具版本、命令、退出码、测试统计、RTL Hash
JUnit XML测试粒度结果每个 testcase 的 pass/fail/skip 与错误信息
scenario_hits.json场景到达和裁决SCN ID、reach count、passed、assertionPassed、证据路径
coverage.dat/report结构与功能覆盖类型、分母、排除项、阈值、增量
log可复现工具执行完整命令、环境摘要、开始结束时间、错误诊断
VCD/FST/trace失败与关键交互定位默认失败保留；关键时序 Intent 可抽样保留
review/signoff独立证据审查明确读取了哪些原始文件及未关闭风险

9.5 Multi-Oracle 独立裁决

关键 Scenario 不能由一个布尔值独占裁决。Oracle Registry 登记 Reference Model/Scoreboard、Invariant/Assertion、Protocol Checker、Formal Property、Metamorphic Relation 与 End-to-End Checker，并记录实现、独立性等级、独立性域和共享 assumptions。关键场景至少需要两个 independenceLevel ≥ 2 且 independenceDomain 不同的有效 PASS。

情形结论处置
只有一个 Scoreboard PASSINSUFFICIENT增加不同独立性域的 Assertion、协议或端到端 Oracle
两个独立 Oracle PASSPASS继续检查到达、证据和时效性
任意有效 PASS 与 FAIL 并存CONFLICT阻断签核；审查命题范围、共享 assumptions、Checker 与 RTL 原始证据
Verdict 未绑定当前 RTL Hash无效执行受影响回归并重新发布证据

系统不设置“Golden Model 永远获胜”或“Formal 永远获胜”的固定仲裁顺序。独立性来自不同错误机制，而不是不同文件名；同一 Agent 从同一 RTL 翻译出的两个 Checker 可能仍属于同一个判断域。

10. 开源 Formal 的补强角色

MoonGlass 当前通过 Yosys/SymbiYosys 生态调用开源 Formal，并根据可用 solver 执行 BMC、cover 与 prove。Formal 特别适合计数器边界、仲裁不变量、握手稳定性、状态机非法状态、场景可达性和小范围时间性质。

模式PASS 的准确含义不能宣称
BMC在给定 bound 内没有反例对无限时间行为已经证明
cover存在一条满足目标的可达路径安全属性成立
prove在当前模型和 assumptions 下归纳证明成功现实环境 assumptions 一定正确

每个 assumption 都必须说明规格依据；property 必须绑定 SCN；FAIL 后需判断 RTL 缺陷、property 错误、环境模型错误或 over/under-constraint。开源 Formal 不支持全部高级 SVA 和商业引擎能力，必要时使用监控寄存器与 immediate assert/assume/cover 改写，同时保留语义说明。

11. 文档体系：消除传统计划与 AIGV 割裂

11.1 唯一权威主链

REQ/SPEC → VI → SCN → TEST / COVER / PROPERTY → EVIDENCE → SIGNOFF

三份基线计划是权威计划，六份 AIGV 文档是风险与闭环视图，二者不能分别维护两套测试清单。MoonGlass 自动生成 aigv_execution_snapshot.md，把当前 RTL Hash、Intent 状态、Coverage Hole 和证据映射回文档目录。

文档唯一职责必须引用

test_plan.md可执行 TEST 项及详细激励、观察和通过标准REQ/SPEC、VI、SCN、Checker、Evidence

11.2 一致性规则

  1. 每个 P0/P1 REQ/SPEC 至少映射一个 VI；不适用项必须说明。
  2. 每个高优先级 VI 至少映射 TEST、PROPERTY 或 Static Check 之一。
  3. 每个 TEST 明确前置状态、激励、观察、Checker、通过标准和证据。
  4. 每个 COVER 说明语义，禁止只有名称没有行为定义。
  5. AIGV 文档不得复制一份不同 TEST ID 的测试清单。
  6. 自动快照不得手工编辑；计划变化应修改权威文档并重新构建智能模型。

12. 分层交付与端到端迭代工作流

AIGV 的方法学目标是端到端闭环，但工程操作不能因此退化为一个边界不明、耗时不可预测的超长 Agent 任务。MoonGlass 使用“外层四步交付 + 内层证据迭代”的双层状态机。

12.1 外层四步交付状态机

步骤主要活动完成判据明确不做
验证规划读取 REQ/SPEC/ARCH 与 RTL Structure；生成三份权威计划、六份 AIGV 视图、Risk、Spec Gap、VI、SCN 与执行批次。计划结构校验通过；关键 Intent 具备前置状态、定向激励、观察点、通过准则和证据要求。不创建完整 Testbench，不运行仿真，不宣称覆盖或签核。
环境搭建创建 driver、monitor、scoreboard、assertion、scenario recorder、coverage sampler 和最小 smoke sequence；复用合适的 VIP/BFM。Python/HDL 语法、导入、编译和 elaboration 通过；Checker 可对最小事务作出裁决。不执行完整风险批次，不追逐覆盖率目标，不做 Formal 签核。
基础回归对各 DUT 执行 reset、idle、一个合法正常事务和已有 smoke，产生首份可信结构化结果。JUnit、result.json、scenario_hits、日志和必要波形真实落盘；Verification State 出现 regression 记录。不因基础 PASS 宣称验证完备，不自动进入无限修复或高风险闭环。
风险闭环按优先级执行高风险 Scenario、Coverage Closure、Assertion、Formal、失败修复、受影响回归和独立证据审查。关键 Intent 关闭；blocking Hole 清零或经批准豁免；签核证据与版本绑定。不接受 Agent 自述完成，不以总覆盖率替代语义闭环。
验证规划 ──plan ready──▶ 环境搭建 ──environment ready──▶ 基础回归 ──baseline evidence──▶ 风险闭环 │ │ │ │ └─ Spec Gap └─ infrastructure blocker └─ first failure └─ signoff / waiver 任一操作收到明确停止边界后，Agent 必须报告当前交付物并停止；只有显式“完整闭环”请求才连续推进。
增量复用原则：四步不是四次从头开发。通过校验且 RTL Hash/规格版本仍适用的计划、环境和证据应复用；变化只重新打开受影响的 VI、SCN、TEST、COVER 和 PROPERTY。

12.2 风险闭环的内层迭代

  1. 读取规格：解析需求、接口、错误、时钟复位、优先级和未知项。
  2. 构建 RTL Structure：计算 RTL Hash，提取 FSM、CFG、COI、writer、domain、protocol。
  3. 推导 Risk 与 Spec Gap：生成可解释风险陈述，保留事实依据和置信度。
  4. 生成 Intent/Scenario：形成可证伪目标、时间关系、边界、方法和优先级。
  5. 同步计划：把 VI/SCN 绑定 TEST/COVER/PROPERTY，更新自动快照。
  6. 选择批次：按优先级、预算与环境复用选择下一批。
  7. 真实执行：运行仿真、Assertion、Formal 或 Static，并保存结构化结果。
  8. 反馈分类：更新 hit、coverage delta、失败证据；未闭环项分类 C1-C6。
  9. 诊断、修复与重跑：区分 RTL Bug、环境 Bug、规格缺口和工具问题；先提高失败可解释性，再执行单假设最小修改、定向与受影响回归。
  10. 独立审查：Review Agent 或工程师读取原始证据，不接受主 Agent 的完成声明。
  11. 签核：全部关键 Intent 闭环，回归与覆盖达标，剩余风险有审批 waiver。
Modelₙ₊₁ = f(Specₙ, RTLₙ, Resultsₙ, Coverageₙ, Formalₙ, Decisionsₙ)

每次 RTL、规格、测试或 assumptions 发生变化，都应重新计算相关状态。RTL Hash 变化后，旧证据不能自动证明新版本；系统可以复用历史信息进行影响分析，但必须重新执行受影响验证。

12.3 失败后的渐进式诊断控制

低 Token 消耗并不代表任务高效：缓存命中、重复读取和相似推理可能使 Agent 长时间卡在同一失败上。AIGV 因此不把“继续推理并继续改 RTL”视为默认策略，而记录 testcase、seed、失败指纹、RTL/Testbench Hash、尝试历史和当前诊断等级。

等级可回答的问题典型证据
L0 最终失败测试最终是否失败？JUnit FAIL、最终输出不匹配、进程退出码
L1 接口/事务哪个接口、channel、transaction 或 checker 首先报错？事务 ID、协议 monitor、scoreboard 条目
L2 时间窗口失败发生在哪个相对阶段或有限观察窗口？关键事件时间戳、聚焦波形、前后状态快照
L3 状态结构哪个 FSM、counter、queue 或 outstanding 状态首先偏离？阶段性 assertion、队列操作日志、计数变化
L4 根因候选哪条机制最可能解释首次偏离？单一可证伪假设、COI、写者与控制条件
L5 根因确认最小修复能否消除失败且不破坏相关回归？定向复现、修复前后差异、受影响与全量回归

当同一失败指纹重复出现，或多次尝试未提升诊断等级时，控制状态进入 DIAGNOSTIC_ENHANCEMENT：暂停盲目修改 RTL，优先增强 staged checker、协议/状态 assertion、事务标识、scoreboard 队列报告和聚焦 trace。增强诊断只能增加观察能力，不得削弱正确预期、删除失败用例或将 RTL 现状改写为 golden behavior。

预算原则：在没有项目基线时，MoonGlass 不设置统一的最大仿真周期数或 wall-clock 时间。硬超时只有在协议、测试或项目给出合理依据时启用；默认控制量是“失败是否重复、证据是否增量、诊断等级是否提升”，而不是武断的统一秒数。

该机制的目标是逐步缩小不确定性，不承诺自动生成“第 183 周期、CH2 重复出队”级别的精确根因。对复杂设计，合理结果也可以是：从最终不匹配收敛到特定 channel、特定事务阶段和有限时间窗口，并给出下一项最有信息增益的观测建议。

13.2 风险加权 Mutation

Mutation 的目的不是测试 RTL，而是测试验证体系。系统针对控制优先级、事务计数、边界、错误处理等高风险机制注入可追踪变异，并将结果分为 KILLED、SURVIVED、INVALID、EQUIVALENT 和 EQUIVALENCE_UNKNOWN。只有 KILLED 进入检出分子；INVALID 不进入分母；EQUIVALENT 必须经过具名审查；SURVIVED 与 EQUIVALENCE_UNKNOWN 默认阻断。

Risk-weighted Mutation Score = Σ(weight of KILLED valid mutants) / Σ(weight of all valid non-equivalent mutants)

高分不自动抵消高风险 survivor。Mutation 必须绑定当前 RTL Hash，且每个结论保留 operator、目标 Scenario、权重和原始证据。

13.3 Residual Risk 与 Waiver

Waiver 不是删除失败或把状态手工改绿。每项豁免应包含目标 ID、原因、影响、适用版本、补偿措施、证据、负责人、审批人和失效条件。RTL Hash、规格或环境发生相关变化时，waiver 应重新评估。

Residual Risk Register 统一记录 Formal 限制、Mutation survivor、Negative Space、Waiver 和工具限制。Agent 可以发现、分类和提出处置建议，但不得伪造审批人。只有包含 approver、rationale 与 approvedAt 的明确批准才能使可接受残余风险进入条件就绪状态。

13.4 Closure Engine 与最终责任

Closure Engine 输出 NOT_READY、CONDITIONALLY_READY 或 READY_FOR_HUMAN_SIGNOFF，并生成绑定 rtlHash 与 verificationSpaceSnapshotId 的 signoff-package.json 和工程可读报告。机器状态是签核建议，不是最终签字；即使所有机器条件满足，仍需要具名工程责任人确认适用范围、工具限制与残余风险。

14. 工程示例：Timeout 与 Late Response

14.1 从标签到风险语义

不可用：Timeout/Late Response: timeout × response

可用：在 dma_read_ctrl 中，事务超时完成后若 AXI R 响应在相邻周期迟到，响应路径可能再次递减 outstanding 或再次产生 done，导致同一请求重复完成、计数下溢或后续事务归属错误。依据为 timeout writer、RVALID/RREADY 完成路径与 outstanding_count 共享状态。

14.2 Verification Intent

目标
验证存在一个在途读事务并触发 timeout 后，在 +1、+2 和边界延迟到达的 R response 不会造成第二次完成、计数重复递减或错误数据提交。
前置状态
outstanding_count=1；请求已被接受；timeout_count=MAX-1；无其他 channel response。
激励
T0 保持 RVALID=0；T1 达到 timeout；分别在 T1、T2、T3 拉高 RVALID/RLAST，并遍历 RRESP OKAY/SLVERR。
观察
done_valid、done_error、outstanding_count、request tag、scoreboard pending queue、timeout/response assertions。
通过
事务只产生一次完成；计数不低于 0；迟到响应按规格丢弃或标记；后续新事务仍能完成；无 assertion/scoreboard failure。
证据
Scenario hit、JUnit、result.json、functional bin、Verilator coverage delta、失败时 FST，必要时 Formal trace。

14.3 Coverage Hole 示例

状态Hole处置
timeout 被测到，但 response 从未在其后到达C3：缺少 late response 定向激励增加 +1/+2 周期 sequence 和对应 functional cross
波形中发生 late response，但无 CheckerC4：缺少重复完成和计数观察补 scoreboard 与 once-only assertion
规格未定义迟到响应应丢弃还是报错C5：唯一预期缺失发起规格决策，更新 SPEC 与 VI
测试 PASS 但 scenario_hits.json 未生成C6：插桩/证据落盘失败修复 recorder 后重跑，不能手工写 PASS

15. 方法学评价指标

15.1 完备性指标

Intent Closure Rate = Closed Critical Intents / Total Critical Intents
Trace Completeness = REQ with VI and Evidence / Applicable REQ
Semantic Coverage = Verified Behavior Bins / Planned Behavior Bins

应同时报告 line、expression/branch、toggle、FSM、functional bin/cross、Intent closure 和 requirement trace completeness，避免单一聚合数字掩盖缺口。

15.2 效率指标

  • 每个新增闭环 Intent 的仿真时间与 Agent token 成本。
  • 每轮反馈带来的 Coverage Delta、Critical Open 减少量与 Novelty Score。
  • 验证规划、环境搭建、基础回归和风险闭环各自的交付时间及重复工作比例。
  • 各模块层级投入：STATIC_ONLY/UNIT_SMOKE/UNIT_FOCUSED/IP_SIGNOFF 的执行成本与缺陷收益。
  • 失败定位平均时间、无效 seed 比例、重复测试比例与同指纹重复修复次数。
  • 每次失败迭代的诊断等级增量，以及进入 DIAGNOSTIC_ENHANCEMENT 后首次获得新证据所需轮次。
  • 每个有效 Mutation 的执行成本、检出率和 survivor 关闭时间。
  • Agent 建议被工程师采纳、修改或拒绝的比例。

15.3 可信性指标

  • Risk 精确率：抽样风险中确有合理结构依据的比例。
  • Spec Gap 精确率与召回率。
  • 错误闭环率：被标记 VERIFIED 但复审缺少到达/独立裁决/证据的比例。
  • Oracle 冲突发现率与同源偏差率。
  • 风险加权 Mutation Score，以及高风险 survivor 数量。
  • 证据可复现率：在干净环境中可重跑并得到一致结果的比例。
  • 变更敏感度：RTL/规格变化后受影响 Intent 被正确重新打开的比例。

16. 局限性与有效性威胁

16.1 语义抽取限制

基于正则与轻量结构分析的 feature 识别可能产生误报和漏报；命名风格、宏展开、generate、复杂接口和跨模块数据流会影响准确性。AST 能提高结构可信度，但不能自动恢复全部系统语义。

16.2 规格质量依赖

若规格只有功能概述，没有周期、错误、优先级和恢复语义，系统只能形成 Spec Gap，不能凭 RTL 反推“正确预期”。

16.3 验证模型同源偏差

若主 Agent 同时生成 RTL、reference model 和 Checker，可能把同一理解错误复制到三处。关键功能应使用独立规格模型、不同实现方式、平行会话复审或人工 golden model。

16.4 Formal 边界

有限深度、简化 harness、错误 assumptions 和状态空间爆炸都可能造成误解。Formal 结果必须报告 mode、depth、solver、property 与 assumptions。

16.5 开源工具差异

Icarus、Verilator、Yosys/SymbiYosys 与商业工具在语言支持、性能、覆盖口径和诊断能力上不同。MoonGlass 的结果适合工程增强与早期质量控制，不应无条件等价为 foundry 或客户签核。

16.6 诊断精度边界

L0-L5 是证据完备程度而非自动根因定位准确率。缺少内部观察点、事务标识、可重复 seed 或足够波形时，系统可能只能定位到接口或时间窗口；诊断等级也可能被冗余日志虚假抬高，因此仍需 Checker 质量和独立复审约束。

16.7 统计有效性

当前方法主要在中小型数字 IP 上迭代，尚需跨协议、跨规模、跨团队、跨工具的公开基准和对照实验。

16.8 Oracle 独立性的可测性

独立性等级和 independenceDomain 目前仍依赖工程建模。不同代码、不同语言乃至不同模型并不自动构成独立判定；共享规格误解、共享参考算法和共享 assumptions 可能形成隐蔽相关性。Multi-Oracle 能降低单点误判，但不能从数学上消除共因失效。

16.9 饱和与 Mutation 的边界

经验性饱和仅对当前有限空间、策略和预算成立；Mutation Score 仅反映所选 operator 对现有验证体系的敏感性。二者都不能证明不存在未建模需求、未知交互或 operator 无法表达的缺陷。

17. 开放研究议程

  1. 风险推导评价：建立带人工标注的 RTL risk benchmark，测量 taxonomy precision/recall。
  2. Intent 质量评价：研究“可执行、可观察、可判定、可追踪”的自动评分与人工一致性。
  3. 场景最小化：在保留交互与边界覆盖的同时减少回归成本，形成 budget-aware test selection。
  4. 诊断信息增益：研究如何量化一条 assertion、trace 或 checker 输出对根因候选空间的缩减程度，并据此自动选择下一观测动作。
  5. 自适应停止策略：利用失败指纹、证据增量、诊断等级和历史执行分布识别无进展循环，而不依赖统一硬超时。
  6. 因果覆盖：从代码被执行扩展为“输入事件是否因果影响目标输出”的覆盖度量。
  7. 变更传播：结合规格 diff、RTL dependency 和证据版本自动计算最小安全回归集。
  8. 多 Agent 独立性：量化不同模型、不同上下文和不同工具证据对同源偏差的降低程度。
  9. 缺陷历史学习：在隐私和可解释前提下，将 bug pattern 用于风险排序，而不直接训练黑盒结论。
  10. 形式化与仿真协同：由 cover trace 生成定向仿真，由仿真 hole 生成 property candidate。
  11. 签核可信计算：对工具、版本、命令、RTL Hash 和证据清单建立可验证 manifest。

18. 结论

MoonGlass AIGV 2.0 将 AI 辅助验证从“生成测试代码”提升为“构造受约束验证空间、选择高价值实验、独立裁决结果并管理停止条件”。其关键不在于某个模型能写多少 Cocotb 或 SVA，而在于是否建立了稳定事实模型、模块分层、可解释风险、可证伪 Intent、可执行 Scenario、版本化证据、独立 Oracle、验证体系敏感性评价和可审计残余风险。

这套方法的核心工程主张可以压缩为四句话：Risk 必须说明可能怎样失效；Intent 必须说明怎样证伪；Oracle 必须说明为何能够独立判断；Signoff 必须说明证据、版本与残余风险在哪里。机器可以输出 READY_FOR_HUMAN_SIGNOFF，但不能替代工程责任人的最终批准。

术语表

术语定义
AIGVAI-Guided Verification；MoonGlass 中结合确定性分析、Agent 推理与真实工具证据的验证方法。
Verification Intent绑定来源、对象、激励、观察、判据和证据的可证伪验证目标。
ScenarioIntent 的可执行实例，包含触发条件、时间关系、边界和方法。
Verification Space由 Feature、Boundary、Interaction、Temporal 与 System State 五维描述，并由规格、结构、协议和预算约束的有限候选空间。
Negative Space因架构无效、协议非法、已证明不可达、规格未定义或预算原因而不执行的候选及其证据化理由。
Multi-Oracle使用不同独立性域的多个判定机制裁决同一 Scenario，并显式处理冲突。
Novelty Saturation在当前空间、探索策略与预算下，连续真实探索没有产生语义新增的经验性停止信号。
Risk-weighted Mutation按风险权重注入缺陷，评价验证体系是否能够检出重要错误的敏感性方法。
Risk Marker由规格或 RTL 结构推导的优先验证假设，不等同于 Bug。
Spec Gap规格与 RTL、需求与实现或时间/优先级语义之间的可定位缺口。
Coverage Hole具体 Scenario 未完成到达、裁决或证据闭环的 C1-C6 原因。
COICone of Influence；影响目标状态/输出的直接与传递来源集合。
Evidence可复现、可定位并绑定版本的日志、结构化结果、覆盖率、property、trace 与波形。
Diagnostic Level从 L0 最终失败到 L5 根因确认的证据完备程度，用于衡量失败迭代是否真正减少不确定性。
DIAGNOSTIC_ENHANCEMENT重复失败且诊断无进展时进入的控制模式：暂停盲改 RTL，先增强 Checker、Assertion、事务追踪与聚焦证据。
