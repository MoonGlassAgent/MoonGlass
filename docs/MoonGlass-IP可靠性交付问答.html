Customer FAQ · Evidence-driven ASIC IP Delivery

MoonGlass IP 可靠性交付问答

客户真正关心的不是 Agent 写了多少代码，而是：规格是否满足、风险是否释放、证据是否可信，以及谁为最终签核负责。

MoonGlass ASIC Design Agent适用版本：v0.9.0+更新：2026-09-10moonglassagent@126.com
最短回答：MoonGlass 不用“AI 说完成了”证明 IP 可靠。

MoonGlass 通过需求与规格追溯、结构化 Verification Intent、风险场景、可复现测试、独立 Oracle、覆盖率、Formal、Lint、综合、RTL 哈希和变更回归构造证据链，并据此形成机器签核建议。最终签核仍应由有责任能力的芯片工程师或组织完成。

可靠不等于零缺陷可靠性交付是对已定义规格和已识别风险提供充分、可复现、可审查的证据。
覆盖率不等于完备性代码覆盖、功能覆盖、需求覆盖、风险覆盖和 Oracle 有效性必须结合判断。
Agent 不能自我签核自然语言结论必须回到日志、测试、覆盖率、属性、波形和版本化工件。

一、基本立场

Q1：MoonGlass 能保证生成的 IP 绝对没有 Bug 吗？核心问题

不能，任何严肃的 EDA 工具、验证方法或工程团队都不应承诺“绝对无 Bug”。

MoonGlass 能做的是把“相信生成结果”变成“审查交付证据”：哪些需求已验证、哪些场景已覆盖、哪些属性已证明、哪些风险仍然开放、使用了什么 RTL 版本和工具版本，都应能够被追踪。可靠性的合理表达是“在约定规格、验证空间、工具能力和证据门槛下达到可接受风险”，而不是宣称数学意义上的零缺陷。

Q2：既然不能保证零缺陷，MoonGlass 的价值是什么？

价值在于提高发现缺陷、解释风险和复现结论的能力，同时减少重复性的工程劳动。

Agent 可以承担规格整理、RTL 实现、验证环境搭建、回归执行、证据归档和缺口迭代；工程师把精力放在规格取舍、架构选择、Corner Case、风险接受和最终签核上。它改变的是工程分工和闭环效率，不是取消工程责任。

Q3：MoonGlass 与普通 Coding Agent 最大的区别是什么？

普通 Coding Agent 主要优化“完成任务”，MoonGlass 还管理阶段、状态、变更、工具和证据。

MoonGlass 使用六阶段流程组织需求-规格、架构、RTL、验证、QA 和综合；前序修改会使已完成的后序证据失效或进入变更响应；验证结论需要绑定当前 RTL，而不能只依据对话中的完成声明。

Q4：MoonGlass 是要替代设计工程师和验证工程师吗？

不是。它更适合替代大量搬运、搭建、执行和整理工作，而不是替代技术判断与责任主体。

规格冲突如何取舍、架构为何这样选、哪些残余风险可以接受、是否满足产品与流片要求，仍需要工程师判断。MoonGlass 让架构到 RTL 再到验证的执行活动更多成为受控的质量工作。

二、需求、规格与验证证据

Q5：如何证明 RTL 满足了客户规格？追溯

通过 Requirement → Specification → Design → Verification Intent → Scenario/Test → Evidence 的双向追溯链证明。

每个稳定需求 ID 应映射到可实施规格、设计位置、验证目标和证据。缺少映射的需求不能仅凭测试通过判定关闭；规格发生变化时，相关设计与验证证据需要重新响应。

客户应查看：需求-规格矩阵、Verification Intent 清单、场景命中记录、测试结果、覆盖率报告、未关闭风险。
Q6：追溯矩阵会不会只是形式完整，实际语义不正确？

会，所以“有 ID”只是最低门槛，不是充分证明。

有效追溯还要检查：测试刺激是否真正触达需求条件、观测点是否能看到预期行为、Checker 是否判断了核心结果、异常路径是否有独立场景。MoonGlass 可发现缺失和结构不一致，但语义合理性仍应接受工程 Review 和隐藏测试检验。

Q7：为什么不能把“所有测试 PASS”直接当成验证完成？

因为测试可能没有有效刺激，也可能没有有效检查。

一个永远不进入目标状态的测试、一个只打印结果而不比较的测试、一个被错误约束屏蔽的场景，都可能显示 PASS。MoonGlass 因此同时检查测试结果、场景命中、Oracle、覆盖率、约束和证据新鲜度。

Q8：MoonGlass 使用哪些覆盖率？

覆盖率应至少分为代码覆盖、功能/场景覆盖、需求覆盖和风险覆盖。

Verilator 可提供行、分支、Toggle 等 RTL 覆盖数据；Cocotb 可收集功能 Coverpoint 与 Cross；追溯矩阵衡量需求是否有验证证据；AIGV 验证态势衡量高风险 Scenario、Intent 和 Coverage Hole 的闭环状态。具体可用项取决于项目工具链和测试实现。

Q9：覆盖率达到 100% 是否意味着可靠？

不意味着。高覆盖率可以证明代码被执行，却不能单独证明行为正确。

弱 Checker 也能跑出高覆盖率。必须结合需求语义、Corner Case、断言、Golden Model、协议 Checker、端到端结果、变异测试和残余风险判断。覆盖率是发现验证空洞的传感器，不是质量结论本身。

Q10：Verification Intent 与普通测试点有什么区别？

Intent 描述要证明的行为语义，测试只是实现该目标的一种手段。

例如“响应与错误同时出现”只是分类；有效 Intent 应表达成：“当事务 CH2 在已有 outstanding 请求时收到错误响应，设计必须只完成一次出队、保持计数不下溢并上报对应错误”。它应同时定义前置条件、刺激、观测点、预期结果和证据。

Q11：Golden Model 和 Checker 本身错了怎么办？

不能把任何单一 Oracle 当成绝对真值。

高风险功能应尽量采用多源 Oracle：Golden Model、协议 Checker、不变量断言、端到端语义比较、Metamorphic Relation 或独立参考实现。Oracle 之间冲突时应进入仲裁，而不是选择有利于 RTL 的结果。必要时用已知向量、反例和变异缺陷检验 Checker 是否真正能报错。

Q12：MoonGlass 如何寻找 Corner Case？

从规格边界、RTL 结构、状态交互、时序关系和已有覆盖反馈共同生成候选场景。

AIGV 将 Feature、Boundary、Interaction、Temporal、State 作为描述维度，结合 FSM、共享状态、计数器边界、背压、复位、并发与错误路径排序。Agent 可以扩展场景，但最终优先级应由风险和证据缺口驱动，而不是无限枚举组合。

Q13：Formal 能证明什么？

Formal 可以在明确模型、约束、属性和深度下证明属性成立、找到反例或证明状态不可达。

它不能自动证明全部产品语义；错误的约束可能造成 vacuity，错误的属性会证明错误目标，BMC 深度不足也不能冒充完整证明。MoonGlass 会记录属性、引擎、深度、结果和日志，并区分 PASS、FAIL、UNKNOWN 与工具限制。

Q14：子模块和顶层是否都跑同样完整的验证流程？

不应一刀切，应按模块角色和风险分层。

简单胶水模块可采用 Lint、接口检查和少量冒烟；算法核心、仲裁器、计数/队列、协议转换、跨时钟控制等模块可能需要独立 Golden Model、断言和覆盖率；顶层重点验证端到端功能、模块交互、并发、复位和系统级错误传播。

三、工具链与结果可信度

Q15：开源 EDA 工具产生的结论可信吗？

在其支持的语言、模型和检查范围内可以形成有效工程证据，但不能自动等同于商业签核。

Icarus、Verilator、Yosys、Slang、SymbiYosys 等工具有明确能力边界。MoonGlass 应保存版本、命令、输入、日志和退出状态，并通过最小自检确认工具真正可用。关键项目仍可接入组织认可的商业仿真、CDC/RDC、Lint、Formal 和综合工具复核。

Q16：如何区分 RTL 缺陷、测试缺陷和工具链缺陷？

通过分层复现和根因分类，而不是看到红色日志就修改 RTL。

先确认编译是否进入设计、测试是否有效启动、Checker 是否命中、工具语法是否支持，再用最小用例、第二工具或第二 Oracle 交叉验证。解析失败、环境缺失和超时应登记为工具/环境限制，不能记成 RTL FAIL，也不能虚报 PASS。

Q17：为什么要保存原始日志，报告摘要不够吗？

摘要用于决策，原始日志用于审计和复现，两者不可互相替代。

Agent 可能误解日志，解析器也可能有缺陷。交付证据应保留原始命令、标准输出、错误输出、JUnit、覆盖数据、波形和工具版本；总体报告只引用这些证据，不应重新创造事实。

Q18：同一工程在另一台机器上能得到相同结果吗？

目标是可复现，但必须固定环境和随机性。

应记录工具版本、依赖版本、命令参数、随机种子、RTL/测试哈希、宏定义、Filelist、时钟复位配置和工艺库。若依赖未固定或测试含非确定行为，就不能承诺逐字节一致，只能比较功能结论和关键指标。

四、Agent 自身风险

Q19：模型会不会“幻觉”出不存在的测试结果？

会，所以 MoonGlass 不接受自然语言自述作为机器证据。

验证完成必须能够找到实际产物，并检查运行状态、退出码、结果结构、RTL 哈希和时间戳。不存在的路径、被截断的输出、过期日志或仅出现在 thinking 中的文件，都不能支持签核。

Q20：设计和验证都由同一个模型完成，会不会产生同源错误？

存在同源偏差，因此高风险目标需要独立证据与适度分离。

主 Agent 可以承担端到端交付，但 Review 应直接读取规格、RTL、测试、日志和覆盖率，而不是接受主 Agent 的总结。必要时使用不同模型、不同上下文、隐藏测试、独立 Oracle 或人工专家 Review。

Q21：模型换了，交付质量会不会变化？

会变化，但门禁和证据标准不应随模型降低。

模型影响需求理解、代码质量、调试速度和 Token 成本；确定性工具、交付 Schema、证据要求和人工签核应保持稳定。模型变更应作为运行元数据记录，并通过基准项目和缺陷注入评估。

Q22：Agent 长时间反复调试，会不会把代码越改越坏？

这是现实风险，需要任务隔离、失败预算、版本控制和诊断优先机制。

MoonGlass 的方向是按任务建立会话，记录修改血缘；重复失败时停止盲改，优先增强 Checker、断言和故障定位证据；RTL 修改后使旧证据失效并重新回归。用户仍应使用 Git 保留可回退基线。

五、变更、回归与项目生命周期

Q23：规格修改后，原来的验证结果还能用吗？

只能在影响分析后部分复用，不能默认继续有效。

MoonGlass 将前序变更传播到已经完成的后续阶段，要求架构、RTL、验证、QA 和综合分别响应。与变更无关且输入哈希一致的证据可保留；受影响的 Intent、Scenario、测试、覆盖率和综合结果必须重跑。

Q24：如何确保报告对应的是当前 RTL，而不是旧版本？

证据必须绑定 RTL、测试和配置的版本或哈希。

当 RTL、Testbench、约束、Golden Model 或关键参数发生变化，相关证据应标记为 stale。只有输入身份一致、工具执行完成且产物有效，证据才可进入当前签核包。

Q25：第三方发现 Bug 后，MoonGlass 如何支持修复？

把 Bug 转化为可复现失败、语义化证据和永久回归资产。

建议流程是：固定原始版本与现场条件；建立最小复现；增强 Checker/断言把“输出错误”收敛为周期、事务、状态和不变量违例；修改 RTL；运行受影响回归和全量回归；将该场景加入风险与追溯体系，防止再次逃逸。

Q26：一键托管会不会为了推进阶段而绕过门禁？

托管可以自动处理可修复缺口，但不能把阻断事实改写为通过。

合理策略是等待 Agent 真正完成任务，再读取门禁；对文档缺口自动修复和重试；对工具故障分类处理；对重大规格影响、不可解释高风险和签核例外要求人工决策。最终报告应列出所有自动处理、强制推进和未关闭项。

六、交付内容与客户验收

Q27：客户最终应收到哪些交付物？验收

至少包括规格、RTL、验证资产、证据、风险清单和可复现说明，而不只是若干 `.v` 文件。

建议签核包：需求/规格与追溯矩阵；架构和接口文档；RTL、Filelist、约束和版本清单；Testbench、VIP、Golden Model、Checker 与断言；测试结果、JUnit、覆盖率、Formal/Lint/综合日志；验证态势；已知限制与残余风险；复现命令和工具版本。
Q28：客户应该怎样独立验收 MoonGlass 交付的 IP？

不要只看演示，应在隔离环境中重跑签核包并加入客户自己的隐藏测试。

建议先验证构建和回归可复现，再抽查需求到证据链，针对最高风险场景加入隐藏测试和变异缺陷，最后用客户认可的 Lint、CDC/RDC、仿真、Formal、综合或 FPGA 原型流程复核。

Q29：如何评价一次交付是否真的比人工流程更好？

同时比较质量、时间、成本和人工决策负担，不能只比较代码生成速度。

推荐指标包括需求一次满足率、追溯完整率、隐藏缺陷逃逸率、变异得分、回归可重复率、证据一致率、修复闭环时间、人工确认次数、Token/计算成本和后续维护成本。

Q30：是否可以先做小规模 PoC 再决定采购？

可以，而且这是更负责任的评估方式。

选择一个边界清晰、具有真实协议和 Corner Case 的数字 IP；预先冻结规格、隐藏测试、质量门槛和人工基线；比较 MoonGlass、通用 Coding Agent 与传统流程。PoC 应同时报告成功、失败、人工介入和未解决风险。

Q31：谁对最终交付和流片结果负责？

责任由采购合同、组织流程和签核角色决定，不能转移给一个模型或软件按钮。

MoonGlass 提供工程执行、证据组织和机器签核建议。产品负责人、设计负责人、验证负责人和签核委员会仍需依据适用标准、工具资格、工艺约束和业务风险作最终批准。

七、当前能力边界

Q32：MoonGlass 当前最适合什么项目？

最适合边界明确的数字 ASIC IP、控制与数据通路模块、常见总线外设及可由 RTL 仿真和开源综合验证的项目。

复杂 SoC、一致性协议、模拟混合信号、安全认证、先进低功耗、多电源域和大规模物理实现，需要更完整的商业工具链、组织方法和专家团队。

Q33：MoonGlass 已经覆盖 CDC/RDC、DFT、低功耗和时序签核了吗？

不能笼统宣称已经覆盖。

MoonGlass 可以辅助生成结构检查、约束、文档和部分开源验证证据，但专业 CDC/RDC、UPF 低功耗、DFT ATPG、STA/物理实现和工艺相关签核仍应接入组织认可的专业工具与流程。没有真实执行证据时，报告必须标记为未验证或外部依赖。

Q34：开源 Formal 能替代商业 Formal 平台吗？

对部分中小模块和明确属性很有价值，但不能普遍替代商业平台。

语言前端、调试能力、容量、性能、应用包和认证支持都有差异。开源 Formal 更适合作为补充证据、早期反例发现和可达性分析；关键签核是否接受，应由项目工具资格要求决定。

Q35：如果验证态势显示绿色，就可以直接流片吗？

不可以把验证态势的绿色直接解释为流片许可。

绿色表示按当前数据模型，已登记 Intent、Scenario、证据和门槛达到配置条件。它不自动覆盖规格本身错误、未建模风险、工艺签核、模拟效应、CDC/RDC、DFT、低功耗、STA、可靠性和系统软件协同。

Q36：MoonGlass 最诚实的可靠性承诺应该怎样表述？

MoonGlass 不承诺自动生成绝对无缺陷的 IP；它承诺努力让交付过程受控、证据可追踪、结论可复现、风险可见、变更可响应。

具体项目的质量水平由输入规格、架构决策、模型能力、验证预算、工具链、工艺环境和人工签核共同决定。客户应把 MoonGlass 视为证据驱动的 ASIC 工程协同平台，而不是“按一下按钮即可承担流片责任”的黑箱。

没有匹配的问题，请更换关键词或分类。
