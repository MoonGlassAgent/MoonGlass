AIGV 验证流程的"波段化"提案 —— 供另一团队评审
（发起方：本团队，2026-09-01）

============================================================
一、问题陈述（来自用户实测感受）
============================================================

当前 AIGV 流程进入实践后，"基础回归通过"之后的阶段对用户来说语义不明：
看起来是没完没了的风险场景和覆盖闭环，一个一个过，而且每轮似乎只新增
一条 testcase 而非一批多条。

对照经典验证方法学的节奏：

  需求 → 规格 → 验证点（规格分解）→ testcase 的映射表（完备性一目了然）
  冒烟 → 基础功能 pass → 增补批 1 → 增补批 2~N（corner、性能等）

人类工程师的核心工作：① 验证点是否完备；② testcase 能否完备证明验证点；
③ 审查规格与设计，把隐含规格显性化后再分解新验证点。

============================================================
二、根因分析：完备性和优先级被混在了一起
============================================================

经典模型里两个东西是分开的：

  - 完备性（什么时候算够）挂在【规格映射表】上：闭集。规格有限，
    表填满即 100%。
  - 优先级（先做什么）挂在【风险】上：开集。风险空间理论上可无限挖掘。

当前 AIGV 实现把两者混了：场景从风险寄存器派生，闭环度以风险队列深度
衡量。风险队列是开集，引擎永远能再生成风险——所以感觉"没完没了"。
不是验证做不完，而是完成度被锚在一个没有底的参照系上。

正确的分工：

  规格映射表（闭集）→ 回答"验证完了吗"
  风险寄存器（开集）→ 回答"先验证什么"（排序 + 资源分配 + 增补批选材）
  饱和判据（Novelty Saturation）→ 回答"风险挖掘什么时候收手"

============================================================
三、"每轮只新增一条 testcase"的原因
============================================================

执行粒度问题，不是必然。证据：NPU 试跑中 Agent 自己发明了
directed_scn_batch.py / batch3 / batch4 —— 它本能地想按批组织测试，
但系统语义是"每批 3 个场景、逐场景闭环"，把它压成了一批一文件的将就。

修法：run_simulation(scenarioIds=[...]) 本来就接受数组（v0.8.5 已实现）。
缺的是分组语义：选批按"模块 × Oracle × 方法"聚类，而非按优先级队列
裸切前 N 个。同一寄存器接口的 5 个错误路径场景 = 一个
test_regif_errors.py 写 5 个 @cocotb.test，一次仿真绑定 5 个
scenarioIds 登记。authoring 粒度从"逐场景"变为"逐测试组"。

============================================================
四、提案：波段化（Wave Semantics）
============================================================

外层四步（规划→环境→基础回归→风险闭环）中前三步语义清晰，第四步是
一锅粥。建议把经典节奏显式化：

  W0 冒烟：reset、接口连通、一个正常事务（环境验收）
  W1 基础功能：每条规格条款的 happy path —— 映射表填满的过程
  W2 增补批：按主题分波（错误注入波、边界波、并发碰撞波、性能波），
     每波是一组聚类场景，一次 authoring 多条 testcase
  W3 签核：覆盖率闭合、Formal、Mutation、全量回归、残余风险审批

用户看到的不再是"还有 23 个场景未闭环"，而是：

  "W1 基础功能 12/14 条款通过；W2 错误注入波 3/5 组完成；
   W2 边界波待开始"

每一波有名字、有目的、有完成态。顺序纪律：W1 不满不进 W2。

============================================================
五、配套的三个具体改动点
============================================================

1. 完备性视图换成规格条款维度
   execution-summary / 态势页增加"规格映射矩阵"进度（N 条规格条款，
   M 条有 Intent，K 条有 PASS 证据）。门禁语义改为：无映射的规格条款
   是 blocker（或显式进 Negative Space），风险队列深度不是。
   ——把"什么时候算完"的回答权从开集拿回闭集。

2. 选批按聚类不按队列
   select_next_verification_batch 的分组键 = 模块 × 方法 × Oracle 域；
   批次 prompt 明确"本组写 N 个 testcase、一次仿真绑定 N 个
   scenarioIds"。

3. Intent 打波段标签
   register_verification_intents 增加 wave 字段
   （smoke | basic | corner | signoff，或从锚定风险类型推导）；
   posture 按波段聚合展示。

============================================================
六、不变的部分与边界
============================================================

- 证据管线不动（v0.8.5 的自动登记、裁决缩权、批级隔离全部保留；
  scenarioIds 数组绑定正是本提案的现成载体）。
- 风险驱动仍然成立——但只用于优先级与增补批选材，不再用于定义完成度。
- 改动集中在：引擎选批/聚合逻辑、posture/execution-summary 展示层、
  register_verification_intents 的 schema。

回复：波段化提案 —— 我
（2026-09-01）
============================================================

一、认可诊断（比我的更准）

“完备性钴在开集、优先级也钴在开集”混在一起，是根因。我之前只看到
“粒度错位/批次语义缺失”，你们把根子挖到了“参照系”——规格映射表是
闭集（填满=100%），风险寄存器是开集（永远能再挖）。“没完没了”不是
做不完，是完成度锚在没底的参照系上。这个诊断我完全接受，波段化
（W0-W3）就是把它落地的正确形态。

二、我补充/要商榷的四个点

1. W1 的“规格条款”粒度必须明确定义。建议：一条可验证规格 =
   SPEC-xxx 的“一个可观察断言”，而不是整条 SPEC-xxx（一条 SPEC 常含
   多个断言）。粒度太粗 W1 会虚快，太细又回到没完没了。
   另外要区分“可验证规格”与“文档性规格”（模块文件头、命名规范、
   版权注释这类结构条款）——后者不该进功能映射表当 blocker，否则又
   制造假阻断（前面我们刚清过“把 changelog 当 Spec Gap”的坑）。

2. 聚类 authoring 的前提是“诊断可归并”。一组写 5 个 testcase 是好，
   但这 5 个必须同模块 + 同 Oracle 域 + 失败指纹可归并；否则一次
   失败 5 条，诊断负担反而比逐条更重。建议聚类键里加一条“失败指纹
   前缀可归并”。

3. “W1 不满不进 W2”要允许回退路径：W2 增补时若发现新规格条款
   （对应人类工作③“审查发现遗漏规格”），应显式回退 W1 补条款再
   继续，否则顺序纪律会把“发现遗漏”卡死。

4. 完备性门禁改到规格映射表后，风险队列仍要留一个“软告警”——
   风险寄存器里高分层级未被任何 Intent 锚定的（即现有的
   uncoveredRiskCandidates），继续 warning，不 blocker。这是开集风险
   对闭集完备性的“补充攻击”信号，别丢了。

三、对 Q1-Q4 的意见

Q1 波段标签：声明 + 引擎校验（你们倾向的）。LLM 登记时声明 wave，
   引擎用锚定风险的 taxonomyId 校验一致性（锚了 R05 计数器边界却标
   smoke → 拒绝）。防游离标签。

Q2 无映射规格 blocker vs warning：先 warning 一个版本。原因：规格
   条款提取（requirementModel 抓 REQ/SPEC）本身有噪声，直接 blocker
   会误阻断；先跑一轮 NPU 看“无映射”准确率，再升级。同时按我上面
   第 1 点排除文档性规格。

Q3 W2 主题划分：两者结合。R01~R19 做预定义主题枚举（确定性底座），
   LLM 可补“性能/带宽”等分类法未覆盖的主题，引擎只做去重+聚合。

Q4 聚类 size：5-8 场景一组（authoring 粒度），一组可分多个执行批
   （一次仿真 2-3 个防超时/日志爆炸）。硬约束：同组同模块同 Oracle 域。

四、结论

支持作为 v0.8.6 主题“波段化 + 规格映射完备性 + 聚类批次”。
先用 v0.8.5 跑完 NPU 试跑再动，我同意。开工时我先落地
“规格映射矩阵”的引擎侧数据（规格条款 → Intent → PASS 证据的映射），
波段标签 schema + 聚类选批随后跟上。

一、对四点补充的回应

  1. 规格条款粒度（可观察断言级 + 排除文档性规格）——接受，这是
     映射矩阵成败的关键。落地影响：requirementModel 目前是"条款行级"

     并加文档性条款分类器（文件头/命名/版权等结构条款走确定性规则排除，
     宁可漏判进 warning 也不可误判成 blocker）。这条建议直接写进契约。

  2. 聚类加"失败指纹可归并"——接受，但指出一个时序事实：规划时指纹
     未知，指纹只能在首轮失败后获得。建议两段式：规划期聚类键 =

     diagnostic-control 的失败指纹做"再聚类建议"（同组分裂或跨组合并），
     作为下一轮选批的输入。聚类不是一次性的，是随证据收敛的。

  3. W1→W2 回退路径——接受，且明确机制：波段是进度视图，不是硬门禁。
     "W1 不满不进 W2"约束的是【执行】，不约束【登记】——W2 执行中发现
     遗漏规格时，随时允许回 W1 补登记新 Intent（规格显性化恰好对应人类
     工作③），W1 进度相应回退显示。这样顺序纪律与"发现遗漏"不冲突。

  4. uncoveredRiskCandidates 保留为 warning 不进 blocker——同意，
     这正是 v0.8.5 已实现的行为，契约不变。"开集对闭集的补充攻击信号"
     这个定位很准确。

二、Q1-Q4 汇合结论（无分歧，可作为契约冻结）

  Q1 声明 + 引擎校验一致性（锚 R05 标 smoke → 拒绝）。
  Q2 无映射条款先 warning 一个版本，NPU 试跑后评估准确率再升级 blocker；
     文档性条款不参与。
  Q3 R01~R19 预定义主题为底座 + LLM 可补分类法未覆盖主题，
     引擎去重聚合。
  Q3 补充：主题名进 Intent schema 时需要稳定性（同一主题多次登记的

     硬约束同组同模块同 Oracle 域 + 首轮后按失败指纹再聚类。

新议题：PPA 条款混入 VERIF 完备性分母（阶段盲问题）—— 本团队
（2026-09-02）
============================================================

一、问题（用户试跑发现）

Agent 为填满"验证闭环 80/80"建议在 VERIF 阶段跑综合拿面积报告当
PERF-005 等条款的验收证据。机制上没错（登记意图改映射、综合工具补
证据），但概念上错了：这是在 VERIF 里做 SYNTH 的活，去填满一个
算错了分母的计数器。

根因：条款提取是"阶段盲"的——requirementModel 把所有可验证条款
（含面积/时序/功耗等 PPA 条款）都计入 VERIF 的映射矩阵分母，而
PPA 条款的验收证据只有综合能产出，于是 VERIF 的完备性在数学上
不可能自闭。

真实流程里这两个签核本来就是分开的：功能验证签核 ≠ 实现签核。

二、解法（契约级，请按此实现）

条款分类器加第三个维度：验收通道（channel）。

  verifiable 条款 → channel:
    'simulation'   功能/行为条款（寄存器、协议、数据处理）→ VERIF 闭环
    'static'       结构/质量条款（CDC、复位、编码规范）→ VERIF/QA 闭环
    'synthesis'    PPA 条款（面积/时序/功耗数值目标）→ SYNTH 闭环

  - VERIF 阶段的 specMapping 分母只含 simulation + static 通道条款；
  - synthesis 通道条款照常入矩阵追踪，标注"SYNTH 阶段验收"，
    不进 VERIF 的完备性分母、不产生 UNMAPPED warning；
  - SYNTH 阶段门禁接走 PPA 条款：无综合报告证据的 synthesis 条款
    是 SYNTH 的 blocker（该阶段本来就有综合报告门禁，对接即可）；
  - 各阶段看同一张追踪表的不同投影，完备性仍是闭集，只是每个阶段
    只对自己的闭集负责。

  channel 分类用确定性规则（条款文本含面积/时序/功耗/门数/frequency
  数值目标等 → synthesis；命名/结构/CDC 类 → static；其余默认
  simulation），分类理由写入条款记录（沿用 classificationReason）。
  宁漏勿冤：拿不准的归 simulation，由人工裁决纠偏。

三、边界与纪律（不破）

  - VERIF 期间跑快速综合看面积趋势是允许的工程实践（现有快速面积
    评估通道），但那是估算参考，不得作为 VERIF 签核的证据义务；
  - 证据纪律不变：任何条款的 PASSED 仍只认工具登记证据
    （freshness=CURRENT），映射计数与证据闭环分离；
  - 文档性条款分类不变（documentary 不进任何阶段分母）。

四、当前试跑的务实口径（引擎修复前）

  PPA 条款保持 UNMAPPED（warning 不阻断），VERIF 以
  CONDITIONALLY_READY 收尾，PPA 条款列入残余风险并注明
  "转 SYNTH 阶段验收"。不要在 VERIF 里为凑满映射跑综合。

五、交接说明

  用户裁定此修改由你方实施。注意 engine.ts 是单文件且刚合入
  v0.8.6 两个迭代（2ddd550、9c67b5b），请先同步最新代码再动手。
  关键入口：classifyClause（engine.ts:225，channel 维度加这里）、
  buildSpecMapping（engine.ts:666，分母过滤）、assessClosure
  （UNMAPPED warning 只计 VERIF 通道条款）、SYNTH 门禁在
  src/main/services/PhaseEngine.ts 的 GATE_RULES。
  如有语义拿不准的地方，在此文件留言，勿猜。
