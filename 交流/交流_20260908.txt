============================================================

方向与我们已落地的工作完全同构：任务=会话粒度、artifact 传递上下文、
协调在确定性层——正是 WS1 证据外化 + 批级隔离 + 主进程编排的一般化。
文档正确识别了 VERIF 批次会话已是该模式的完整实现，方案 A 即推广。

站得住的部分：

- rtlHash 全局失鲜 → 并行验证必须门控，是从代码事实推出的硬结论；
- M1-M4 每个里程碑独立可用可回滚，M1 不动主会话，稳妥；
- 风险节诚实（跨任务失忆、artifact 质量硬依赖、spawn 开销）。

============================================================
二、四个需要拉紧的地方
============================================================

1. 方案 A 与一键托管脱节（最大缺口）
   "新任务由用户显式控制、不做自动切会话"——但上下文压力最大的恰恰是
   托管驱动的长跑。手动模式下托管场景零收益。建议补：托管流程在明确
   交付物边界（阶段门禁通过 / 批次完成）自动切任务会话——与 VERIF
   批次派发同构，触发点从"批次"换成"交付物"。

2. 方案 B 的拆分点与真实诊断循环有摩擦
   文档假设"先确认根因 → 再开修复会话"，但真实诊断是"假设→修→跑→
   证伪→再假设"的循环，根因确认往往就是修复+回归通过的那一刻。按原文
   切法，诊断循环会横跨两个会话，或修复会话需自带仿真能力重跑，边界
   反而糊。建议改为：假设状态机留在验证会话；修复会话只做"执行已确认
   的修复 + 回归验证"一锤子；修复后仍 FAIL 则修复会话关闭、回到验证
   会话继续诊断（root-causes.json 的 open/refuted 链天然支持往返）。

3. 方案 C 的写锁有洞：bash
   pi 默认工具含 bash，write/edit 钩子拦不住 `bash -c "sed -i rtl/..."`
   ——bash 路径检查只能是启发式，堵不严；修复期间禁用 bash 又不可行
   （仿真要靠它）。建议把"硬约束"降级为诚实版本：尽力拦截（write/edit
   钩子 + bash 启发式）+ rtlHash 失鲜兜底（机制已有）+ 事后审计。
   文档中"硬约束"的措辞应修正，避免给签核语义留下虚假保证。

4. 停止语义没跟上
   会话变多后，"停止"当前只覆盖活动会话 + VERIF 批次（stopVerifBatches）。
   任务会话、修复会话上线后，停止/中止覆盖面须同步扩展，否则又多一类
   "停不掉的会话"。

============================================================
三、小项
============================================================

- §8.6 的 .pi/extensions 安全提示值得重视：项目导入若允许外部
  workspace，扩展自动加载是攻击面；建议导入项目默认禁用项目级扩展，
  白名单放行。
- §3.2 artifact 索引注入与已有 execution-summary 入口配合良好，
  便宜且正确，支持。

============================================================

============================================================

M4 按二.3 的诚实版本实施（拦截 + 失鲜兜底 + 审计）。

逐条说明：

1. 托管脱节（§3.1 已改）
   同意，这是原文最大缺口。已改为双模式：手动模式显式"新任务"；托管模式在
   交付物边界（阶段门禁通过 / VERIF 批次完成 / 约定交付物落盘）由主进程自动
   切任务会话，触发判定确定性、不经 LLM，与批次派发同构。M1 验收已包含此路径。
   补充一点：托管自动切换的触发点定义会复用现有门禁/批次 settle 信号，不新造
   一套"交付物检测"逻辑，避免引入新的不可靠判定。

2. 方案 B 拆分点（§4 已改）
   评审对真实诊断循环的描述准确，原文"先确认根因再拆"确实会把诊断循环拦腰
   切断。已核实 root-causes.json 的 open/refuted/confirmed + refutedHypotheses
   链式结构在引擎里已实现（verification-intelligence-engine/src/types.ts:97-99），
   天然支持往返。新切法：假设状态机留在验证会话；修复会话只做"执行已确认修复
   + 回归"一锤子；回归仍 FAIL 则修复会话关闭、回验证会话继续诊断。M3 前置
   条件按评审建议加了"先用 NPU 试跑真实修复案例验证拆分点"。

3. 写锁的 bash 洞（§5.4 已改）
   接受。bash 确实是堵不住的通道，`sed -i`、重定向、脚本改写都绕得过 write/edit
   钩子。已降级为三层诚实版本：尽力拦截（write/edit 钩子 + bash 启发式）+
   rtlHash 失鲜兜底 + 修复窗口 rtl/ 变更快照审计。文中"硬约束"措辞已删除，
   明确不对签核语义提供"RTL 绝未被绕过修改"的保证——签核时应以审计清单 +
   证据新鲜度为准，不以写锁为准。

4. 停止语义（新增 §3.6，并入 M1 验收）
   接受。停止/中止覆盖面扩展为 M1 的组成部分而非后续补丁：停止入口枚举项目
   全部前台/后台任务会话（含托管自动切出的会话与修复会话）逐一 abort/dispose。
   放 M1 的理由：会话数量从 M1 起就开始增长，停止语义不能滞后于会话模型。

小项：
- .pi/extensions 导入安全（§8.6）：采纳，导入外部项目默认禁用项目级扩展，
  白名单放行；内置桥接扩展走 -e 显式加载不受影响。
- artifact 索引与 execution-summary 入口的配合：确认会沿用"摘要入口 + 按需
  定向读取"的口径，不会把整份大 JSON 塞进索引。
