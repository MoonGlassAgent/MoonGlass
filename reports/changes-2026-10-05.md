## 2. 解析内核重写（最高优先级）

### 问题

界面上的条款分母是错的，且需求文档被整体丢弃。以真实项目复现（只读复制到临时工作区、跑真实引擎）：

| 指标 | 小数分频器（CLK_DIV_FRA） | GMAC |
|---|---:|---:|
| 源码行数 | 25 | 74 |
| **产出条款数** | **71** | **390** |
| `module_specification.md` 贡献 | 71 | 347 |
| **`product_requirements.md` 贡献** | **0** | **7** |
| `requirements_traceability.md` 贡献 | 0 | 36 |
| 一行产出的最大条款数 | 6 | **27** |
| 条款文本含表格分隔符 `\|` | 69 / 71 | 291 / 390 |

极端样本：GMAC `module_specification.md:106` 一行产出 **27 条条款**。

### 根因（`packages/verification-intelligence-engine/src/engine.ts`）

1. **同一行的每个 ID 都拿到同一份整行文本** —— `for (const id of ids)` 内把 `lineText`（整行）交给每个 ID，各自生成条款；
2. **全局首次出现获胜** —— `seen` 集合在**任意首次出现**处登记 ID，导致 `module_specification.md` 的"关联需求 ID"列（追溯引用）把 `REQ-*` 全部提前认领，`product_requirements.md` 的正式定义被整份跳过；
3. **表格行被当作规范陈述** —— 条款正文是 markdown 表格行原文，包含字段值（接口名/方向/位宽/时钟域），无法作为可验证义务阅读；
4. **追溯矩阵被当作定义来源** —— 纯链接表也按 ID 出现次数生成义务（GMAC 36 条）。

### 改法

**契约：一条义务 = 文档 ID 列里的一条陈述。**

| 原行为 | 新行为 |
|---|---|
| 不区分文档角色 | `requirements_traceability.md` 识别为**纯链接表，零义务**；`module_specification.md` 定义 `SPEC-*`、`product_requirements.md` 定义 `REQ-*` |
| 表格行 = 整行文本 | **表感知解析**：区分「定义列」（表头恰为 ID 列，如 `规格 ID`/`需求 ID`）与「引用列」（如 `关联需求 ID`） |
| 一行 N 个 ID → N 条条款 | **一行一条义务**；同行其余同命名空间 ID 视为该陈述的别名 |
| 首次出现获胜 | **定义优先**：ID 的定义是它出现在**自身文档 ID 列**的那次；其余出现记为引用 |
| 条款正文 = 整行 | 正文取**验收类列**（验收标准/通过标准/关键约束/检查点/预期），单元格用 `｜` 连接（`；` 是断言分隔符，用它拼接会把字段边界误判成断言边界） |
| 无追溯信息 | 新增 `references`（本行引用的 ID）与 `citedIn[]`（本 ID 被引用的位置）；只被引用、从未定义的 ID 记入 `unresolvedReferences`，**不生成义务** |

分类（`clauseKind` / `channel`）与特征提取改为**按整行口径**：验收通道（PPA/静态）是整行的属性，只看验收列会漏判「输入时钟频率 200MHz」这类量值措辞，使 PPA 条款误回 VERIF 完备性分母。

### 效果（同一复现脚本，修复后）

| 指标 | 小数分频器 | GMAC |
|---|---|---|
| 条款总数 | 71 → **66** | 390 → **186** |
| `product_requirements.md` 贡献 | 0 → **35** | 7 → **105** |
| `requirements_traceability.md` 贡献 | 0 | 36 → **0** |
| 单行最大条款数 | 6 → **3** | 27 → **9** |
| 文本完全重复的组 / 条 | 26 / 55 → **4 / 8** | 121 / 264 → **0 / 0** |
| 条款文本含 `\|` | 69/71 → **0/66** | 291/390 → **0/186** |
| 场景总数 | 59 → **46** | 383 → **171** |
| 重复期望文本的场景 | 20 组 / 43 → **4 组 / 8** | 119 组 / 260 → **0 / 0** |
| 追溯链接 | — | `citedIn` 186/186、`references` 81 |

定点核对（小数分频器 `SPEC-IF-003` / `REQ-IF-003`，修复前是 4 条同文本条款 → 4 个场景）：

```
SPEC-IF-003#a  «建立/保持时间满足»                    SCN-8EE662BC
SPEC-IF-003#b  «与 i_load 同拍采样»                   SCN-8FDCAED1
REQ-IF-003     «边界值加载功能正确（REQ-FUNC-002）»    SCN-CC125ABA   ← 来自 product_requirements.md:186
```

**剩余 4 组重复文本是合法的**，不是缺陷：`SPEC-IF-003` 与 `SPEC-IF-004` 是两根不同信号（`i_div_int` / `i_div_frac`），约束措辞恰好相同。两根信号必须分别验证，不得因文本相同而合并。

### 为什么这同时解决了「不收敛」

每个未闭环条款派生一个 `CLAUSE_DERIVED` 场景，且 `criticality = 0.8` → 按 `engine.ts` 的规则**每个场景要求 2 个独立 Oracle 通过**。修复前一条真实行为被物化成 4～6 个独立场景，其中同文本的别名场景**不存在能让一个通过而另一个不通过的证据** —— 要么一起通过（纯浪费），要么永久停在 OPEN。

GMAC 383 个场景里 **260 个（68%）属于此类**，所以「未闭环关键场景 278」中有相当部分是**结构上不可能闭环的幻影义务**。

## 3. 运行时口径统一（P0）

### 3.1 移除「态势重建即进展」——最高价值的收敛修复

`src/main/services/AgentService.ts` 两处（决策拍与常规拍）：

```ts
const advanced = judgeRunLoopAdvanced(posture.state, after.state) || postureFresh
```

`postureFresh` 是**假信号**：任何引擎重建（登记裁决、登记证据、重算映射）都会刷新 `verification-posture.json` 的 `generatedAt`。后果是 `noProgressStreak` **恒为 0**，「连续无进展熔断」永不触发，循环只能烧到墙钟上限。

实测与 GMAC 账本完全吻合：`lastBeats` **17 条全部 `advanced=true`**，而 `exploration-history` 49 轮 `NO_PROGRESS`、`newlyClosedScenarioIds` 恒为空，最终停在 `paused-breaker / max-wall 276/240 分钟`。

修复后进展只认闭环计数（`openIntents` / `blockingHoles` / `coveredClauses` / `failedRegressions`）。
`judgeRunLoopAdvanced` 已把"态势从无到有"算作规划拍进展，故**首拍规划仍被正确判为进展**，不误伤 W0。

> 归属：该条件由被回退的提交 `1993bbf` 删除过；回退使其复活，本轮重新删除。

### 3.2 批次完成判定分离「本批新增证据」与「历史证据重放」

`src/main/services/verif-batch-verdict.ts` 原来用 `readRegisteredScenarioIds` 只判断"该场景**历史上**是否登记过"，
因此「只读旧失败证据 + 登记裁决 + 重建态势」的会话可被判完成，且**该契约单独无法区分旧证据重放与本批新增结果**。

| 改动 | 内容 |
|---|---|
| 读取口径 | 新增 `readScenarioRegistrationTimes`：场景 ID → **最近一次登记所在文件的 mtime**（多文件取最新）；保留 `readRegisteredScenarioIds` 兼容入口 |
| 契约 | `VerifBatchVerdict` 新增 `freshScenarioIds` / `replayedScenarioIds`（可选字段，向后兼容） |
| `complete` 语义 | **保持不变**（= 全部登记 + 态势在批次开始后重建）。诊断类批次按约定交付登记即为完成，若因重放而判失败会误杀合法路径 |
| 可观测性 | 仅有历史登记时给出结构化 reason：`本批未取得新增执行证据，涉及场景仅有历史登记：…（complete 表示批次会话契约完成，不等于场景通过或验证进展）` |

收敛后果由 3.1 承担：重放批次不改变闭环计数 → 计入 no-progress streak → 触发 `rule-stall` 熔断。
`complete`、`场景通过`、`验证进展`、`签核` 四个词由此各自只有一个判定处。

### 两条硬口径

1. **记录通过 ≠ 当前有效通过**：`PASSED` 仅在「证据文件存在 + 证据版本 == 当前 RTL + 证据不晚于态势 + 态势版本 == 当前 RTL」同时成立时计入 `validPassed`，否则计入 `needsRevalidation`（历史通过）。RTL 改动后旧 PASS 不再冒充当前有效。
2. **没有评估不能推断就绪**：缺 `closureAssessment` / `signoffPackage` 时签核状态只能是 `unknown`。

附带：分母与明细不一致时标记 `mapping-incomplete`（明细少于分母 → 差额计入未确认；明细多于分母 → 分母置为未确认，不给出假分母）；无可读态势时显示「尚未生成」而**不显示零值统计**（零值最易被读成"已完成"）；synthesis 通道条款单列、不进 VERIF 完备性分母。

### 移除两处虚假绿色

| 位置 | 原行为 | 现行为 |

**属于事实、可直接核对**：§2 的全部实测数字（可用临时工作区复现脚本重跑）、§6 的验证结果、
§3.1 引用的 GMAC 账本数据。

**最需要人工确认的一点**：真实项目首次重建后，**场景结构会变化**——幻影义务对应的场景消失
（小数分频器 59→46、GMAC 383→171），保留场景的 ID 稳定但正文收窄，
而磁盘上 `scenario_hits.json` 里的**旧 hit 会照旧算作通过，可能偏乐观**。建议重建后抽查关键场景的证据有效性。
